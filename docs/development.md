# 開発ルール

Sashimono の開発で守ることをここにまとめる **このファイルが大本**で、
`CLAUDE.md` / `AGENTS.md` / `.cursor/rules/` はここを指しているだけ
ルールを変えるときはここを直す

---

## 1. 環境

### Python は必ず仮想環境のものを使う

```
.venv\Scripts\python.exe
```

**素の `python` を使わない** 開発機の `python` は PEP 514 のランチャースタブで、
標準入力からスクリプトを読ませると**応答が返らなくなる** ヒアドキュメントと
組み合わせると対話モードで起動し、出力ファイルが数 GB まで膨らんだことがある

### 導入

```
.venv\Scripts\python.exe -m pip install -e ".[dev]"
```

字幕起こし（`asr`）と AI 連携（`ai`）は**既定では入れない** 合計 2 GB を超えるので、
ソフト内の導入ボタンから必要になった時点で入れる

## 2. 実装したら必ず検証する

```
.venv\Scripts\python.exe tools\verify.py
```

ruff（書式・規約）→ mypy（strict）→ pytest をまとめて走らせる **1 つでも落ちたら
終了コードが非 0** CI もこれと同じものを走らせるので、手元で通れば CI でも通る

CI だけは pytest を 4 つのプロセスに分けて並べて走らせる（pytest-xdist）
`verify.py` は環境変数 `SASHIMONO_TEST_WORKERS` に数（または `auto`）が入っていれば
並列に、無いか `0` なら直列にする 手元の既定は直列で、試すときだけ立てる

```
$env:SASHIMONO_TEST_WORKERS = "4"; .venv\Scripts\python.exe tools\verify.py
```

並べると、同じワーカーで先に走った試験の状態に頼る試験や、時間を測る試験が
CPU の取り合いで落ちることがある 同じワーカーにまとめたい試験には
`@pytest.mark.xdist_group("名前")` を付ける（`--dist loadgroup` で効く）
遅いテストの上位 30 本は、毎回 pytest の出力の最後（`slowest 30 durations`）に出る

個別に走らせたいとき:

```
.venv\Scripts\python.exe -m ruff format src tests tools
.venv\Scripts\python.exe -m ruff check --fix src tests tools
.venv\Scripts\python.exe -m mypy src tests
.venv\Scripts\python.exe -m pytest -q
```

**AI（Claude Code / Codex / Cursor）に実装させた場合も同じ** 実装 → リファクタ →
`tools/verify.py` まで含めて 1 つの作業とする 「動くコードを書いた」で止めない

時間変換とファイルの錠は、対象のコードや試験を変えた PR と週 1 回の CI で mutation
testing も走る 条件式や境界値を機械的に変えても試験が落ちなければ、試験の検出力が
下がったとして CI を落とす 手元で確かめるときは次を使う

```
.venv\Scripts\python.exe -m pip install -e ".[dev,mutation]"
$env:PYTHONUTF8 = "1"
.venv\Scripts\python.exe -m pytest tests/core/test_timebase.py tests/test_locks.py --hypothesis-seed=0 --gremlins
.venv\Scripts\python.exe tools/check_mutation.py
```

## 3. 書き方

### コメントは「なぜ」を書く

日本語で書く **何をしているかはコードを読めば分かる** 書くのは、そう書いた理由と、
そう書かないとどうなるか

```python
# 秒は必ず分数で持つ 浮動小数にすると保存と読み込みを繰り返すだけで値が動く
```

将来の自分と他人が「これは消してよいのか」を判断できるようにするのが目的

### 文章に句点（まる）を使わない

コメント・docstring・画面や例外に出す文言・Markdown・設定ファイルのコメント・
コミットメッセージ・PR の本文、どれも句点で文を終えない

- 行の終わりや閉じ括弧の前では、何も付けずに終える
- 1 行に 2 つの文を続けるときは、半角空白で区切る
- 読点（、）はこれまでどおり使う

```python
# 秒は必ず分数で持つ 浮動小数にすると保存と読み込みを繰り返すだけで値が動く
```

**データとしての句点は例外** 字幕整形が句点として扱う文字の一覧や正規表現、
テストの入力データ（起こし結果の字幕文など）は、中身そのものなので残す
ここを消すと字幕の改行位置や句読点の処理が壊れる

リポジトリの中のファイルは `tools\punctuation.py` が見分けて検査する
（`tools\verify.py` と CI に入っているので、落ちたら気付ける）
コミットメッセージと PR の本文は道具では見ないので、書くときに気を付ける
うっかり書いてしまったら次で直せる

```
.venv\Scripts\python.exe tools\punctuation.py --fix
```

### テストは失敗の仕方を書く

`assert` が通ることではなく、**壊れたときに何が起きるか**をテスト名とコメントに残す

```python
def test_the_animation_uses_the_whole_length(self) -> None:
    # 並び順をフレーム番号だと思うと、300 フレームの動きが 2 フレームで終わる
```

### TODO を残さない

`TODO` / `FIXME` をコードに書かない やり残しはまず今のブランチで直す
（下の「懸念点は同じブランチで直す」） 今のブランチで直せない物だけを
[[実装ロードマップ]]（Obsidian）か GitHub の Issue に出す コード内の TODO は
誰も見ないまま残る

### 型は strict で通す

`mypy --strict` が通らないものは入れない `type: ignore` を書くときは、理由を
同じ行か直前のコメントに残す

## 4. 設計の約束

### コア層は GUI に依存しない

`src/sashimono/core/` は PySide6 を import しない CLI からもテストからも AI からも
同じ API で動くことが、AI 連携とテスト容易性の前提になっている

### 変更は必ずコマンド経由

UI の操作も AI の操作も同じ `Command` を発行し、同じ Undo スタックに載る
モデルを直接書き換えない

### パラメータ定義は 1 形式

自前のエフェクトも AviUtl の配布スクリプトも、同じ `ParameterSpec` に載せる
設定 UI の自動生成・プリセット・キーフレームがこれ 1 つで済む **新しい種類の
パラメータを足すときは、AviUtl の制御文字と対応が付くかを先に考える**

### 好みが分かれる所は、設定画面から変えられるようにする

**動きを勝手に決めない** 人によって答えが変わる項目は、決め打ちにせず
設定（`表示 → 設定…`）に出す 実装する前に「これは全員にとって同じ答えか」を
1 度考える

答えが分かれるのは、たとえばこういうもの

- 自動で何かが変わる（大きい素材でプレビューの画質を落とす、など）
  速さを取る人と画質を取る人がいる
- 速さと品質の釣り合い（控えの大きさ、先読みの量）
  機械の速さで答えが変わる
- 見た目の好み（表示する単位、色、並び順）
- 操作の癖（確認を出すか、どこまで自動で進むか）

決め方

1. **既定は、知らない人が困らない側にする** 何も設定しない人が一番多い
   自動で軽くする側を既定にして、嫌な人が切れるようにする
2. 置き場は `ui/workspace.py` の `Preferences`
   プロジェクトではなく**本人と機械**に付く（同じプロジェクトを速い機械で
   開いたら等倍で見たいことがある） プロジェクト設定と混ぜない
3. 壊れた値で起動を止めない 項目ごとに既定へ戻す
4. **測った値があるなら、設定画面にも書く** 「なんとなく軽くなる」ではなく、
   どれを選ぶと何 ms になるのかを見て選べるようにする
5. 切ったら本当に止まることを試験で押さえる 切っても効いたままなら、
   設定がある方が質が悪い

### 画面の色はテーマから取る

画面の色は暗い・明るい・Windows の設定に合わせる、から選べる（`Preferences.theme` 既定は暗い）
切り替えは再起動なしでその場で効く 色をその場で書くと、そこだけ前のテーマのまま残る

- 色は `ui/theme.py` の `Colors` に足し、明るいテーマの値を `_LIGHT` にも書く（片方だけだと試験が落ちる）
- 自前で描く所（タイムライン・グラフ・波形など）は描くたびに `Colors` を読む 切り替えると
  `Colors` の **QColor の中身を書き換える**ので、先に受け取って持っている色も一緒に変わる
  `QColor(Colors.X)` で写してから変えるのはよいが、`Colors.X` そのものを書き換えない
- 部品ごとのスタイルシートに色を書くときは `themed_style(部品, lambda: f"...")` で当てる
  `setStyleSheet(f"...{Colors.X.name()}...")` と書くと、その時の色が文字列に残る
- 色を焼き込んだ絵や HTML（再生ボタンの印、会話の欄、素材一覧の印）は `theme_signals().changed`
  につないで作り直す つなぐのは部品の関数にする（lambda だと部品が消えても外れない）
- 色をその場で書いてよいのは、地がテーマで決まらない所だけ（プレビューの映像の上に重ねる枠、
  色の見本の文字など） `tests/ui/test_light_theme.py` の `_FIXED_COLORS` に理由と一緒に足す
- 足した色は、文字なら地との比 4.5、線や印なら 3 以上にする（同じ試験が WCAG の式で見る）

### 狭い画面でも崩さない

1366x768 と 1280x720 のノート PC で、窓を画面いっぱいに広げて使えること 窓の最小の幅は
パネルの最小の幅の和で決まり、1 つでも広い部品があると窓が画面からはみ出す（β の前は 1367
画素あり、1366 の画面で設定パネルの「100.00 %」と見出しの ✕ が欠けた）

- ボタンを横 1 列に並べない 狭いパネルでは折り返す（`ui/flow_layout.py` の `FlowLayout`）
- 選択肢の長さ（素材・書体の名前）でコンボボックスの最小の幅を決めない（`narrow_combo`）
- 数値欄の幅は決め打ちにせず、範囲の端の値と単位から決める（`TrackEditor.number_width`）
- 設定パネルは横に巻物にしない 中身が欠けずに入る幅をパネルの最小の幅にする
- プレビューの下の帯は、狭いときに全体の長さと「再生品質」の名前を丸ごと隠す（縮めて欠けさせない）
- 初めて開いた窓は画面の使える広さに収める（`main_window.initial_size`）
- 高さも詰める 書体の行の高さで窓の最小の高さは変わる（GitHub Actions の Windows では手元より
  84 画素高く、1280x720 の中身 640 を超えた） タイムラインの最小は目盛りとトラック 1 本ぶん、
  AI のパネルの会話と入力の欄の最小は行の数で決める 試験は 640 より 100 画素低いことを求める

`tests/ui/test_narrow_window.py` が、本番のスタイルシートを当てた窓を 1366x688 と 1280x640
（画面からタスクバー 48 と題名の帯 32 を引いた中身）、それと窓の最小の幅で開き、部品が
重ならないこと・数値と ✕ が欠けないことを見る Windows の見た目とオフスクリーン
（`QT_QPA_PLATFORM=offscreen` 書体の幅が違う）の両方で通す 2026-10-02 に測った窓の最小の
幅と高さは、Windows の見た目で 1001x416、オフスクリーンで 1166x366

### 半透明の重ね合わせはプロジェクトの設定

AviUtl2 と YMM4 は、半透明の絵を sRGB で符号化した値のまま混ぜる（黒の上に 50% の白で 128）
光の量（リニア）で混ぜると 188 になる どちらで混ぜるかは `ProjectSettings.blending` に持ち、
`プロジェクト設定` から `SetBlending` で変える（Issue #65） 作品の見た目そのものなので、
本人の好み（`Preferences`）ではなくプロジェクトに付ける 別の機械で開いても同じ絵にするため

- 新しく作るプロジェクトは sRGB 読み込んだ AviUtl・YMM4 の素材が同じ明るさで出る
- 項目の無いファイル（形式の版 2 まで）はリニアで開く そのころはリニアで描いていたので、
  既定で開くと保存したときより半透明の所が暗くなる
- 設定に従うもの: クリップの重ね合わせ・不透明度（フェードの効果も不透明度を下げるだけなので
  同じ）・合成モードの不透明度の効き方・入れ子のシーン・切り抜き・画面の写し取り・書き出し
- 設定に関係なく sRGB のもの: 合成モードの色の式、YMM4 の場面切り替えのフェード
  （どちらも実物で測って合わせてある）、文字の影と縁（文字の絵を作るときに 8bit の sRGB で混ざる）
- 設定に関係なくリニアのもの: エフェクトの中の計算（ぼかし・グローなど） 合成先のキャンバスを
  エフェクトへ渡すときは、符号化を戻してから渡す（`EffectProcessor.canvas_encoded`）

エフェクトの中までは切り替えていない 後光・やみおちエフェクトは合成の切り替えだけで
YMM4 との差が大きく縮み（83.7 → 66.6、13.2 → 2.6）、中を sRGB にした場合と比べる
書き出しがまだ無いため 推測で変えない

### 版の出どころは 1 か所

`src/sashimono/__init__.py` の `__version__` だけ `pyproject.toml` はここから読む
2 か所に書くと、配った版と中身の版が必ずずれる

### 本人の置き場の名前は 1 か所、旧名は印で囲む

設定・退避・キャッシュ・導入した実行環境の場所は `src/sashimono/core/userdirs.py` から取る
`%APPDATA%` などを各所で直に組み立てない 改名で置き場の名前を変えたときに、
引き継ぎの側と食い違う

改名前の名前（古い拡張子・形式名・置き場）は、読む側と引き継ぐ側にだけ残す
その範囲は「旧名を残す」の印の行で囲む（印の後ろに `: ここから` と `: ここまで`、
ファイルごと残すときは `: このファイル全体` を付ける 書き方は `core/io/serialize.py` を見る
ここに印そのものを書くと、この文書まで一括置換から外れる） 名前を一括で
置き換える道具はこの範囲を飛ばす 囲まずに書くと、一括置換で新しい名前に書き換わり、
改名前に保存した作品が開けなくなる（`tests/test_legacy_names.py` が落ちる）

### Y 軸は上が正

テキストの位置・影のずれ・変形・マスク、すべて**正の値で上へ動く**
過去に変形とマスクだけ逆になっていて、配布エイリアスを描いて初めて気付いた
新しく座標を扱うものを足すときは、向きをテストで固定する

例外は次の 2 つだけで、どちらも**表示名に「下が正」と書く**

| エフェクト | 設定 | なぜ |
| --- | --- | --- |
| `brush_fill` | 模様の中心・ずらし・ノイズの位置と速さ | YMM4 のブラシの値をそのまま持つ |
| `particles` | 放つ位置 Y | YMM4 のパーティクルの値をそのまま持つ |

どちらも「YMM4 の設定をそのまま渡して同じ絵になる」ことを優先している
シェーダの中で画面の向きへ直すので、写す側で反転してはいけない

### 画素の値には印を付ける

プレビューの画質を落とすと（1/2・1/4）、合成そのものが小さくなる 位置・大きさ・ぼかしの強さの
ような**画面の画素で決める値**は、描くときに合成の画素へ縮めないと、プレビューだけ 2 倍・4 倍に
出る（Issue #151 書き出しは等倍なので正しい）

- エフェクトの数の項目は `TrackSpec` の単位が `px`（`px/フレーム` も）なら縮める 単位が違う
  画素の値（`px/秒` の速さなど）は `pixels=True`、単位は `px` でも画面の画素ではない物は
  `pixels=False` を書く 書き忘れは `tests/engine/test_preview_quality.py` が拾う
- シェーダの中に書いた画素の長さは `u_pixel_scale` を掛ける 1 テクセルずつ読む刻みのような
  バッファの細かさの話は掛けない
- テキストと図形は描く座標ごと縮める（`render_source_framed` の `scale`） 文字の中の制御文字の
  大きさのように、設定の欄に無い画素の値も漏れない
- AviUtl スクリプトは画面の画素のまま走らせ、返った位置と大きさを描く直前に縮める
  スクリプトの値はどれが画素かを定義から読めない
- プレビューの外枠とドラッグの換算も同じ割合（`canvas_scale`）を使う
- 縮めると 1 合成画素に満たなくなる物（画面 1 画素ずつの粒、細い縁やベベル）は、切り上げて
  1 合成画素で濃く塗らない 書き出しを縮めた絵では周りと平均されて淡くなる ノイズは覆う画面の
  画素の粒を平均し、縁取りと縁の反射は端数の割合で薄める（#173）

### クリップが最初から持つ欄と、置いたときの大きさ

YMM4 のアイテムと同じく、置いたクリップは 描画（反転 → 配置）と 音声（音量 → フェード）の欄を
印付きのエフェクト（`Effect.fixed`）で持つ 中身と並びは `core/commands/fixed.py` の 1 か所

- 付けるのは置く所すべて（素材の読み込み・テキストや図形・エイリアス・字幕の焼き込み・
  互換の読み込み） 互換の読み込みが写した配置や音量には印を付け、同じ種類を 2 つ並べない
  フィルタと場面切り替えは自分の絵を置かないので描画の欄を持たない
- 欄は列の末尾（YMM4 はエフェクトを掛けた絵を最後に置く） 位置を渡さずに足したエフェクトは
  最初の欄の前に入る（`AddEffect`）
- 既定のままの配置と反転は描かずに飛ばす（`EffectDefinition.idle_when`） 全クリップに付くので、
  通すと全クリップが中間のバッファを通る 実物のテンプレート 500 本の 1636 枚が、欄を付ける前と
  1 画素も変わらないことを確かめた
- 前の版のファイルは開いたときに欄を足さない 設定パネルは既定の値で見せ、触ったときに
  欄を足して値を入れる（1 回の取り消しで戻る）

置いたときの大きさは**素材の画素のまま**（拡大率 100% が素材の画素 YMM4・AviUtl と同じ
YMM4 は画像と動画で書き出して測った 下の「拡大率 100% の大きさを測る」）
クリップの `native_size` で持つ 素材を置いたときと互換の読み込みは真、項目の無いクリップ
（前の版のファイル）は画面に収める 真のときだけ保存に書くので、形式の版は上げていない
（前の版の本体は項目を捨てて開き、画面に収めて描く） 大きさは素材の解像度から出し、控えの
大きさやプレビューの画質に左右されない 設定パネルの描画の組の「画素で置く」で切り替えられる

### 別のプログラムを起こすときは窓を出さない

配る本体は窓を持たない（コンソールの無い）プログラムで、そこから ffprobe のようなコンソールの
プログラムを起こすと、そのたびに黒い窓が一瞬出る 前は素材の回転を読むのに ffprobe を
起こしていて、読み込み・再生・控え・字幕起こしのたびに窓が出た

- まず PyAV で読めないかを見る 回転は頭の 1 枚を復号した絵の `rotation` で読む
  （`engine/decode/probe.py` の `_display_rotation`）
- どうしても起こすときは `creationflags` に `CREATE_NO_WINDOW` を付ける（`runtime.py` の
  導入と同じ） 窓を見せたい物（Claude Code のログインの `CREATE_NEW_CONSOLE`）だけが例外
- アシスタントの `claude.exe` は Claude Agent SDK が起こし、印を渡す口が無い SDK の transport の
  部品が見ている `anyio` を、`open_process` に `CREATE_NO_WINDOW` を足す包みへ差し替える
  （`ai/console.py` #228） SDK のファイルは書き換えない 自前の transport を渡す口もあるが、
  渡すと SDK が繋ぐ前に整える所（`can_use_tool` の繋ぎ方・会話の再開）を通らなくなる
  SDK の中の作りが変わって差し替え先が無くなれば何もしない（窓は出るが会話はできる）
- 素材を調べた結果（`probe_media`）は場所と中身の印（更新時刻・大きさ・ファイルの番号・状態の
  変わった時刻・頭と尻の 128KB の要約）を鍵に覚える デコーダは作るたびに調べるので、覚えないと
  再生やシークのたびに素材を開いて頭の 1 枚を復号する 更新時刻と大きさだけだと、同じ大きさの
  別の素材で上書きして時刻を戻した物を見分けられない
- 印でも真ん中だけの書き換えは見分けられない（見分けるには全体を読むことになる） 使い回すのは
  読み込んだ後に素材を開き直す所（デコーダ・控え・字幕起こし）と割り切り、素材を読み込む操作
  （読み込み・ドロップ・テンプレートや .exo の素材・AI の読み込み）は `forget_probe` で捨ててから
  調べる 同じ素材を同時に何本ものスレッドから頼まれたら、開くのは 1 回で、ほかは待つ
  捨てると世代が進み、捨てる前に始まった調べは待たず、その結果も覚えない 世代を持つのは
  調べている最中の物がある場所だけで、調べ終われば消す（扱った場所の数だけ増え続けない）
- 回転は映像ストリームごとに読む 頭の 1 枚を待つ間に読むパケットは 256 まで 絵を出さない
  映像でファイルの終わりまで読まないため

### 動画の映像と音声を分けて置く

音声のある動画は、既定では映像と音声を別のトラックへ置く 音声が 1 本でも混合の方式で
2 つのレイヤーに分け、ゲームの録画（ゲームの音とマイクの声）のように音声ストリームが
2 本以上あれば音ごとに別のトラックへ置く（利用者の要望 レイヤー 1 に映像、レイヤー 2
以降に音） 前は 1 本目の音だけを置き、2 本目以降はタイムラインのどこにも無く鳴らなかった

- 混合の方式 置いたレイヤーに絵だけのクリップ（`audio_stream` が `None`）、その次のレイヤー
  から音ごとに音だけのクリップ（`show_picture` が偽）を並べる 次のレイヤーが埋まっていたら
  飛ばして後ろを見て、無ければ一番後ろへ足す（`core/commands/layers.py` の `layer_after`）
  間へ差し込むと、後ろのレイヤーの名前（番号）と並びが食い違う
- 分ける方式 音ごとに空いた音声トラックへ置き、足りなければ作る
- どちらも全部を 1 つのリンクの組にし、音のクリップはどれも固定の音量とフェードを持つ
  置くのは `AddTrack` と `AddClip` の列で、1 回の取り消しで全部戻る
- 波形は音ごとに解析して控える（`MediaAnalyzer` の鍵に音声ストリームの番号を持つ）
  前は素材だけを鍵にしていて、音声 4 本の動画を置くと 4 本の音のレイヤーがどれも 1 本目の
  波形になった どの音を鳴らすかは鳴らす所と描く所で同じ `heard_stream` から取る
  1 本目の控えの鍵は前と同じにして、前に作った控えを作り直さない
- 設定の「動画の映像と音声」（`Preferences.media_split`）で 1 本のクリップにまとめる前の
  置き方に戻せる（音声が 2 本以上あれば 1 本目だけ） 置く入口（ファイルのドロップ・読み込み・
  素材一覧からのドラッグと配置・AI の道具・ドラッグ中の目安）はどれも `insert_media` /
  `place_media` へ `split_audio` で渡す コアの既定は偽（まとめる） 入口が必ず設定を渡す
- 前の版の設定（`multi_audio` 音声が 2 本以上の動画だけの置き方）は読み替える 1 本目だけ
  （`first`）を選んでいた人はまとめる側になる 読まないと、更新しただけで置き方が変わる
- 互換の読み込み（YMM4・AviUtl）は分けない どちらのアイテムも 1 本で絵と音を持つ

### 混合の方式にエフェクトのレイヤーは無い

分ける方式には、フィルタを置くための映像トラック（名前が `FX` と番号 右クリックの頭に
「フィルタを置く」が出る）がある 混合の方式では持たない（利用者の要望 分けない方式では
普通のレイヤーに何でも置く）

- 「＋ トラック追加」は種類を選ぶメニューを出さずにレイヤーを 1 本足す 右クリックも
  サブメニューではなく「レイヤーを追加」を直に置く（利用者の要望 選べるのが 1 つだけの
  メニューは手間が増えるだけ）
- フィルタは普通のレイヤーへ置く 置き先は範囲に絵のある一番手前より手前の空いたレイヤーで、
  無ければ一番手前へ普通の名前（レイヤー N）で足す（`free_layer`）
- 前の版で作った `FX` と番号のレイヤーは普通のレイヤーとして扱う 名前も中身も変えないので、
  分ける方式へ変換すればまたエフェクトトラックになる（`is_effect_track` は映像トラックだけを見る）

### 設定パネルのキーフレームと初期値

- キーフレームはクリップの頭から数えたフレームで持つ 設定パネル・グラフエディタ・
  タイムラインの印のどれも、再生位置からクリップの頭を引いて渡す 前は設定パネルの ◆ が
  再生位置のまま打っていて、頭が 0 より後ろのクリップでは別の時刻に点が入っていた
- 数のスライダーの値の横に ◀ ◆ ▶（利用者の決定） ◆ は再生位置にキーを打つ・消す
  （再生位置がクリップの外なら押せない） ◀ ▶ は前後のキーへ再生位置を動かす キーの値は
  隣の入力欄で直す（再生位置のキーの値が変わり、無ければ打つ） ◆ は主の 1 本だけに当てる
- 初期値へ戻すのは行の名前のダブルクリック（数はスライダーのダブルクリックでも）
  数値欄のダブルクリックは数字を選んで打ち直すため、色のボタンは 1 回目の押下で色の窓が
  開くため、そちらは使わない キーフレームのある値は再生位置のキーだけを初期値にする
  （無ければ初期値のキーを打つ ほかのキーは残す 利用者の決定） 文字・ファイル・格子と
  「画素で置く」は戻さない（うっかり戻すと打った中身が消える・初期値が決まらない）
  ダブルクリックで戻すかは設定（`Preferences.double_click_reset` 既定は入）で切れる
- グラフエディタは選んだクリップに付いていく（キーのある最初の値を出し、上の欄で選び直す）
- クリップを割る（`SplitClip`）・無音をカットする（`RippleCut`）ときは、後ろの部分のキーを
  割った所を頭にして数え直す（`AnimatedValue.split_at`） またぐ区間には形を変えない点を足す
  （前は最後のフレーム、後ろは頭） 範囲の外に出たキーは捨てる 前はキーをそのまま写していて、
  後ろのクリップにも同じ位置付近に同じキーが入った
- スライダーのダブルクリックは、2 回目の押下をスライダーへ通し、動かさずに離したときだけ
  初期値へ戻す 押下を握りつぶすと、クリックの直後に押したまま動かす調整が効かなくなる

### 設定パネルに出す欄

- 今の値で使わない欄は出さない（`SourceDefinition.unused` 隠すだけで値は残す）
  図形は種類ごとに描く所が読む項目だけ（前は四角形にも星空・集中線・音声波形などの欄が
  60 近く並んだ） 場面切り替えは、向きを押し出しとスライド、動かす・手前にする場面を
  スライドと重ねる、イージングを進み具合を使う切り替え方のときだけ出す
- 場面切り替えは下の絵をそのまま入れ替えて描き、不透明度・合成モード・クリッピングを
  読まないので、描画の組を出さない
- 〔＋ エフェクト〕に並べるのは選んだクリップに効く物だけ（タイムラインの右クリックと同じ
  `effects_for_clip`） 音だけのクリップに映像のエフェクト、絵だけのクリップに「音」を並べない

### 書き出すシーン

書き出しの窓の「書き出す物」でメインかシーンを選ぶ 既定はメイン（開いている物で出る物が
変わると、書き出した物を取り違える） シーンを選ぶと、そのシーンのタイムラインをメインの
所へ差し込んだプロジェクトを書き出す 範囲はシーンのタイムラインで指定した物、出力先の
既定の名前はプロジェクト名とシーンの名前

### 字幕起こしの GPU

pip で入れた CUDA ランタイム（`nvidia-cublas-cu12` など）は DLL を `nvidia/*/bin` に置き、
CTranslate2 はそこを探さない GPU で読む前にその置き場を DLL の探し道と PATH へ足す
（`asr/environment.py` の `register_cuda_libraries`） それでも CUDA のライブラリが読めなければ
CPU で起こし直し、何が読めなかったかと「環境を更新」での入れ方を知らせる（`gpu_fallback_notice`）
CUDA ランタイム無しで入れた後も「GPU を使う」に印を付けて環境を更新すれば足せる
音声が何本もある素材は「起こす音声」で起こす音を選ぶ（`TranscribeOptions.audio_stream`）
字幕は素材と音声ストリームごとに持つ（`MediaItem.transcripts` 保存の形式 8 利用者の要望）
前は素材に 1 つだけで、音声 2 を起こすと音声 1 の字幕が置き換わり、分けて置いた音声 1〜4 の
クリップすべてに同じ字幕が出た 番号を省くと 1 本目（`transcript` は 1 本目の字幕）
形式 7 までのファイルの字幕は 1 本目の音声の物として読む
- 音を鳴らすクリップにはその音の字幕、絵だけのクリップには 1 本目の字幕を出す
  （`projection.subtitle_stream`）
- 字幕の編集の命令（`SetTranscript` `SetSegmentText` など）は `stream` を持つ
- 字幕パネルは見る音を選べ（音声が 1 本なら出さない）、整形・無音カットも見ている音の字幕と
  波形で決める タイムラインで選んだクリップの素材と音に付いていく
- 起こし直しで既に字幕がある音は、窓なら置き換えるかを尋ね、AI の道具なら `replace` が
  真でなければ断る
- 起こしの依頼は順番待ちの列（`TranscriptionService`）に入れて 1 本ずつ走らせる 窓からも
  AI の道具からも同じ列 終わった物はどれも頼んだ素材と音の字幕へ入る `transcription_status`
  は走っている物と待っている物を並べる

字幕の焼き込み（`burn_subtitles`）は話し手（素材と音声）ごとに別のレイヤー（分ける方式では
映像トラック）へ入れる 名前は「字幕 音声 N」（素材が違えば素材の名前も） 1 本にまとめて
いたときは、音声 1 と 2 が同時に話す所で前の字幕が切り詰められて欠けた 窓で焼き込む話し手を
選び（既定は全部）、字幕パネルの〔選んだ行を置く〕と右クリックの「テキストとして置く」は選んだ
行だけ（選んでいなければ再生位置の 1 行）を置く 見た目は、タイムラインで選んでいるテキストの
クリップがあればそれを写し（フォント・色・位置・縁取り・影・エフェクト 本文だけ差し替え
ID は振り直す）、無ければ既定 どちらで置くかを窓に書く AI の道具は `place_subtitles`
どれも 1 回の取り消しで全部戻る

字幕から焼き込んだテキストのクリップは出どころの字幕の行（`Clip.subtitle_origin` 素材・音声・
行の ID）を持つ `replace_subtitle_text` はこの印が直した行を指すクリップだけを一緒に直す
本文の一致で探すと、手で書いたタイトルがたまたま同じ本文だと書き換えた（PR #231） 印は
あるときだけ保存に書くので形式の版は上げていない 印の無い前の版の焼き込みは直さず、返事の
`unmarked_text_clips` に数える 話し手と印は投影した字幕の出どころ（`ProjectedSubtitle.media_id`
と `stream`）から取る 置いたシーンの中の字幕は `clip_id` が外側のシーンのクリップになるので、
そこからたどると素材が分からず、シーンの中の別々の話し手が 1 本にまとまって欠けた（PR #231）
「どのクリップがこの音のクリップか」は `core/projection.py` の `subtitle_voice`（トラックの種類で
変わる聞こえる音を、素材の字幕の番号にそろえた物）1 つで比べる 字幕パネルの一覧の印・時刻・
分割の時刻と、無音カット（`plan_cuts` の `stream`）が使う 音を見ずに最初のクリップを使うと、
リンクを外して音声 2 だけ切り詰めたときに音声 1 の位置で字幕を割り、無音を切った（PR #231）

1 件だけで返事の上限を越える行も上限に収める 字幕の一覧は 2000 字を越える本文の頭だけを
返して `truncated` を付け（軽い形でも segment_id を添える）、全文は `segment_id` を渡して
8000 字ずつ（`text_offset` と `next_text_offset`）読む ほかの一覧も、1 件が長すぎれば長い
文字列と配列から半分ずつ切り詰めて `truncated` を付ける（PR #231） 上限に収まるかは、件数・
続き・案内まで組み上げた返事の長さで確かめる（行だけで見ると外側の分で越えた）

AI の道具の返事は打ち切られない長さに収める 配布版の Claude Code は MCP の道具の返事を
25000 トークン（`MAX_MCP_OUTPUT_TOKENS` の既定）で打ち切ってファイルへ退け、アシスタントには
ファイルを読む道具を渡していないので続きが読めない（字幕 328 行の get_subtitles がそうなった）
一覧の道具（get_subtitles・list_clips・list_media・list_tracks・list_effects）は `offset` と
`limit` で切り、JSON で 12000 字（`MAX_RESULT_CHARS` 日本語 1 文字 1〜2 トークンで上限の半分
ほど）を超えないよう件数を減らし、続きがあれば `next_offset` と書き方を添える 字幕は言葉・
時刻・素材と音声で絞れ、`compact` で行の番号・時刻・本文だけを返す list_effects は `kind` を
渡したときだけパラメータまで返す `replace_subtitle_text` は「誤 → 正」の組をまとめて当て、
字幕と、字幕から置いたテキスト（本文が直す前の字幕 1 枚と同じテキストのクリップ）を 1 回の
取り消しで直し、置き換えた数と当たらなかった組を返す

AI の道具 `transcribe` も `audio`（1 から タイムラインの「音声 N」と同じ番号）で選べる
省くと 1 本目 本数は `list_media` の `audio_count`

テキストも使わない欄を隠す タイマーの書式が空ならタイマーの 4 つ、書式があれば文字、
数え下げを切れば長さ、縦書きなら行揃えと組み方、縁取りの太さが 0 なら縁取りの色、
影のずらしとぼかしが 0 なら影の色（キーフレームで動く値は使う側に数える）

### 部分フィルタの範囲をプレビューで動かす

部分モザイク・ぼかしと部分フィルタを積んだクリップを選ぶと、プレビューに範囲の枠（橙の点線）を
出す 2 つ以上積んでいれば、設定パネルで最後に触った物 フィルタのクリップにも出す
（外枠は出さないが、画面全体に掛けて隠したい所だけを選ぶのが一番よく使う形）

- 枠は `engine/render/region_outline.py` が、範囲の値を描く側と同じ道で送って求める
  原点は絵の中央（フィルタは画面の中央）、Y は上が正 範囲より後ろの配置と反転は範囲ごと絵を
  動かすので枠も動かす 部分フィルタの後ろ（固定の欄の手前まで）は範囲を動かさない
- 掴んだ所は、枠の写しの逆で範囲の値の座標へ戻してから値を決める 後ろの配置で拡大・回転
  していても、掴んだ所と動く所が合う 一致は GPU で描いた絵と比べる試験
  （`tests/engine/test_region_outline.py`）が見る
- 中で移動（Shift で片方の向き） 角で幅と高さ（向かいの角は動かない Alt で中心を保つ）
  辺の真ん中で片方だけ 上の丸で回転（Shift で 15 度刻み） 範囲をクリップの枠より先に見る
- 楕円も外接の四角で動かす キーのある値は再生位置のキーを動かす（設定の「キーフレームのある
  値を動かしたとき」に従う 既定は ◆ と同じ再生位置） 離したときに 1 段で取り消せる

### タイムラインの磁石（吸着）

クリップを動かす・端を伸び縮みさせる・素材を置くときに、近くの位置へ吸い付く（`ui/timeline/snap.py`）
吸い付く先は利用者の決定で、ほかのクリップの頭と終わり（どのトラックでも 動かしている物と
リンクした相手は除く）・再生位置・キーフレームのコマと書き出し範囲の端 動かしている物は
頭と終わりのどちらか近い方で吸い付く 吸い付いた所に黄色い縦の線を一瞬（0.6 秒）出す

- 入り切りはタイムラインの上の〔磁石〕（`Preferences.timeline_snap` 既定は入） 文字では
  入と切が見分けにくかったので、印（`resources/magnet*.svg`）を描き分け、入は押し込まれた地と
  アクセント色の縁にする 印は配る版の自己診断（「同梱の絵」）が揃っているかを見る
  吸い付く距離は `表示 → 設定…` の「吸い付く距離」（画面の画素 既定 8）
- 動かしている途中で Shift を押している間は吸い付かない Alt は離したときに窓のメニューへ
  移り、Ctrl は選び足しに使っている Shift を押してから掴むと範囲で選ぶ操作になるので、
  掴んでから押す

### プレビューの磁石と配置のテンプレート

プレビューで絵の中を掴んで動かすと、画面の端と中央、今のコマに映っているほかの物の端と
中央へ吸い付き、吸い付いた所に黄色い線を引く（`ui/preview_handles.py` の `snap_offset`
利用者の要望） 端は見えている範囲（回した絵は四隅を囲む四角）で比べる 吸い付く先は掴んだ
ときに 1 度だけ集める（動かすたびにほかの物の枠を作ると、テキストの多い画面で遅れる）

- 入り切りはタイムラインの磁石とは別（`Preferences.preview_snap` 既定は入 `表示 → 設定…`）
  距離はタイムラインと同じ「吸い付く距離」（画面の画素）
- Shift を押している間は吸い付かない（タイムラインと同じ） Shift は片方の向きだけに動かす
  決まりでもあるので、押している間は向きをそろえるだけになる

設定パネルの描画の組の「揃える」は 9 つのボタン（四隅・辺の中央・中央）で、見えている範囲の
端を画面の端へ付ける（中央は範囲の中央を画面の中央へ） 大きさはプレビューが描く側と同じ枠
（`outline_of`）から取るので、画素で置いた素材や回した絵でも端が合う 今のコマに映って
いない物は寄せずにステータスバーへ理由を出す キーフレームのある値は、プレビューで動かした
ときと同じ決まりで点を打つ

### リンクとグループを解く・割る

置いた動画の映像と音はリンク（`link_group`）で一緒に動き、束ねたクリップはグループ
（`group_id`）で一緒に選ばれる 利用者から見るとどちらも「一緒に動く組」なので、
〔グループ解除〕（`UngroupClips`）はリンクも一緒に外す（利用者の要望 外した後は映像と音を
別々のレイヤーへ動かせる） 2 つを 1 つの仕組みにまとめなかったのは、リンクが「同じ素材の
絵と音」として読み込み・変換・AI の道具からも見られているため

割るとき（`SplitClip`）は、リンクは今までどおり後ろの片割れどうしを新しいリンクにする
グループは、2 本以上をまとめて割ったときに後ろの片割れどうしを新しいグループにする
（`new_groups` 割る命令を出す側が 1 つの新しいグループを決めて全部へ渡す 取り消しは 1 回）
1 本だけ割ったときは後ろも元のグループに残る

グループが束ねるのは選ぶ・動かす・消す・割る所だけで、設定パネルの値は押した 1 本だけに当てる
（AviUtl のグループ化と同じ 前は 1 本の拡大率を変えると束ねた全部が一緒に変わった）
仲間として引き込まれただけのクリップはタイムラインが覚えていて（`TimelineView.edit_targets`）、
Ctrl や範囲・囲みで自分で選んだクリップにはこれまでどおりまとめて当てる 束ねた全部の値を
揃えたいときは、囲むか Ctrl で選び足す 全体を一緒に拡大・移動したいときはグループ制御を使う
主のクリップと同じグループの仲間には、選び方に依らず値を当てない（設定パネルの
`_also_for_others`） 2 本を選んでからグループ化すると、どちらも自分で選んだ物のまま残り、
引き込まれた仲間を外すだけでは連動し続けた（利用者の手元） プレビューの枠での移動・伸縮・
回転も掴んだ 1 本だけを動かす（まとめて動かすのはタイムラインの上）

ロックしたレイヤーのクリップを含むグループは、まとめて割る・消す・切り取る・動かす・伸び縮み
させる操作を断り、ステータスバーに理由を出す（利用者の要望 前はロックした仲間だけを残して
ほかだけが割れ・動き、束ねた物の頭や長さが食い違った） 何も選ばずに再生ヘッドで割るときは、
そのグループだけを飛ばしてほかは割る 押して選ぶだけなら断らない

### グループ制御

AviUtl の拡張編集のグループ制御と同じ考えの生成オブジェクト（`GROUP_KIND` 右クリックの
〔追加〕→〔グループ制御〕） 自分では描かず、置いたトラックより手前（並びの後ろ 混合の
方式では番号の大きいレイヤー 分ける方式では画面で上の V）の「対象レイヤー数」本（0 なら
手前のすべて 既定は AviUtl と同じ 1）の、同じ時刻に描くクリップ 1 本ずつへ掛ける

- 配置（位置・拡大・回転）と反転はクリップ自身の配置の後ろへ足す 支点は画面の中央なので、
  グループの位置を中心に拡大・回転され、グループの位置だけずれる 不透明度は掛け合わせる
  足したエフェクトはクリップ 1 本ずつ、クリップ自身のエフェクトの後ろ・配置の前に掛ける
  （`engine/render/groups.py` 描くときだけで、プロジェクトは書き換えない）
- まとめて 1 枚に描いてから掛ける形にしなかった AviUtl のグループ制御はフィルタ効果を
  対象の各オブジェクトに掛ける（1 枚にするのはフィルタオブジェクト） YMM4 の GroupItem も、
  「合成する」を切った物は中身 1 つずつに掛ける（`compat/ymm4/template.py` 手元の配布物
  75 本の中に GroupItem の型名が 132 回出てくる） 1 枚にすると、ぼかしで隣の物とにじみ合い、
  合成モードや切り抜きの相手も変わる
- 「1 枚の絵として扱う」（`GROUP_AS_ONE` 既定は切）を入れると、受け持つトラックのその時刻の
  絵を入れ子のシーンと同じ道で 1 枚に重ねてから、配置・不透明度・エフェクトを掛ける
  （重なった半透明どうしが透けない YMM4 の GroupItem の「合成する」に当たる） 受け持つ
  トラックは外の重ねでは描かない
- 本数は描かないトラックも含めて数える（AviUtl は非表示のレイヤーも番号に数える）
  描かないトラックのグループ制御は効かない 入れ子は近いグループから当てる
- 値はグループ制御の時刻で読んで止めた値にして当てる クリップの時刻で読むと、頭がずれた
  クリップで動きがずれる
- プレビューの外枠はグループで動いた所に出す（点線 掴んで動かすのはクリップ自身の配置）
- タイムラインには受け持ちの範囲を常に出す（`ui/timeline/group_reach.py`） 受け持つトラックの
  グループ制御の時間の幅へ薄い紫を敷き、グループ制御の頭から受け持ちの端まで括弧を引く
  選んでいるグループ制御の物は濃くする 対象レイヤー数 0 なら並びの端まで
- AviUtl の `.exo` の グループ制御 は写さない 手元の配布物 270 本に 1 度も出てこず、項目の
  名前と意味を実物で確かめられないため 読み込むと未対応の記録に「オブジェクト: グループ制御」と
  数える YMM4 の GroupItem は今までどおり中身へ移す

### タイムラインの描画の速さ

目標は「スクロール / ズームが 60fps」（1 回の描画が 16.7ms 以内 判定は 95 パーセンタイル）
`tools/bench_timeline.py` が画面に出さずに画像へ描かせて測る `--media` を付けると、
ffmpeg でその場で作った動画（`testsrc` 1280x720 10 秒）と音（`sine` 440Hz）を指す
クリップを並べ、サムネイルと波形の解析を済ませてから測る 続けて、同じ並びでサムネイルだけ・
波形だけ・どちらも描かないときの速さも出す（判定には入れない 重い所を分けるため）

```
.venv\Scripts\python.exe tools\bench_timeline.py --clips 100
.venv\Scripts\python.exe tools\bench_timeline.py --media --clips 100
```

2026-09-25 に手元（Windows 11）で測った 95 パーセンタイル（ms） 1920x420 に 8 トラック
（映像と音声が 4 本ずつ）、1 本 90 フレーム 同じ機械でも 1〜3ms は揺れ、ほかの重い仕事が
走っていると全体表示の 95% が 30ms を超えた回もあった

| 並べた物 | 全体を表示 | スクロール | ズーム |
| --- | --- | --- | --- |
| テキスト 100 本 | 5.4 | 4.8 | 4.0 |
| テキスト 1 万本 | 4.4 | 5.9 | 18.0 |
| 実素材 100 本（#201 の直し前） | 54.0 | 58.3 | 51.3 |
| 実素材 100 本 | 18.2〜20.9 | 16.1〜16.2 | 16.9〜17.8 |
| 実素材 100 本 サムネイルだけ | 9.5 | 10.0 | 7.5 |
| 実素材 100 本 波形だけ | 17.9 | 15.1 | 14.9 |
| 実素材 100 本 どちらも描かない | 8.9 | 7.0 | 5.1 |

重かったのは波形 見えている列ごとに Python で値を切り詰めて `drawLine` を呼び、束ねる所
（`Waveform.envelope`）も列ごとに回していた 1920 幅に音声トラック 4 本で 7000 列を超える
どちらもまとめて求めるようにして 3 分の 1 になったが、まだ全体表示とズームは予算の縁にいる
残りは列ごとの `QLineF` を作って渡す所（波形だけで 8ms ほど） サムネイルは 1 回 1ms ほど
テキストより中身なしでも重い（8.9 と 5.4）のは、素材の名前の札と値の線を描く分

#205 で波形を線から画像に変えた 1 列 1 本の縦線を numpy でまとめて塗った画像を作り
（線で描いていたときと同じ画素になる）、同じ倍率の間は作った画像を貯めて貼る
（`ui/timeline/painter.py` の `_WaveformImages` 上限 32MB） クリップ全体を 1 枚にするので、
再生ヘッドが動くたびの描き直しとスクロールでは作り直さない 幅が 8192 画素を超える
クリップ（長尺素材を大きく拡大した時）は見えている所だけを作る 倍率を変えた直後の 1 回は
作り直すので、道具は「波形の画像を貯めずに毎回作るとき」も出す また `--media` の
クリップは頭を 1/100 秒ずつずらした 全部が同じ所から始まると画像が 1 枚で済み、実際より
速く出る

同じ機械・同じ日に、直す前と後を交互に測った 95 パーセンタイル（ms 静かな時の 1 回）

| 並べた物 | 全体を表示 | スクロール | ズーム |
| --- | --- | --- | --- |
| 実素材 100 本（#205 の直し前） | 21.1 | 13.5 | 13.3 |
| 実素材 100 本 | 7.6 | 6.9 | 6.3 |
| 実素材 100 本 波形の画像を毎回作る | 13.1 | 11.3 | 11.9 |
| 実素材 100 本 波形だけ（直し前） | 19.0 | 10.7 | 10.0 |
| 実素材 100 本 波形だけ | 6.4 | 4.7 | 4.3 |

波形だけと、どちらも描かない（4.6）の差が波形を描く分 13ms ほどから 2ms ほどになった
ほかの重い仕事が走っている間は、直した後でも全体表示の 95% が 25ms まで跳ねた

波形には音の効果を大まかに映す（`engine/audio/shape.py` 利用者の要望） 鳴らす音を作り直さず、
列ごとの最小・最大へ効き方だけを掛ける 音量調整（キーフレームも）・音量フェード・トラックの
音量は倍率、ディレイはずらした波形を足し、リバーブは残響の長さで減る尾を後ろへ伸ばす
モノラル化・音程・パンは大きさがほぼ変わらないので映さない 効き方は画像を貯める鍵に入れる
（音量を変えたら作り直す） 2026-09-30 に `--media --clips 100` で測った 95% は、全体表示
9〜15ms・スクロール 7〜9ms で、予算の中に収まった キーフレームで動く値は、音量だけでなく
フェード・ディレイ・リバーブも列ごとのコマで解く（頭のコマの値だけで描くと、動かしても波形が
変わらなかった PR #231） ディレイは列ごとの間隔・量・繰り返しで前の列から取り、リバーブは
0.1 秒刻みの長さごとに尾を作って列ごとに選ぶ
見えている範囲だけを作る広いクリップ（`WAVEFORM_IMAGE_MAX_COLUMNS` 超）は、ディレイ・リバーブの
形が届く長さ（`shape_history_frames`）だけ手前も同じ列の幅で取って形を掛け、見える列だけを貼る
手前を取らないと、見える範囲の手前で鳴った音のやまびこや尾がスクロールで消えた（PR #231）
手前の列は `WAVEFORM_HISTORY_MAX_COLUMNS` までに抑える

### 前の音を読む音のエフェクト

リバーブ・ディレイ・音程の調整は前の音を読む（`EffectDefinition.audio_history`） ミキサは
クリップの頭から数えた 16384 サンプルの区切り（`HISTORY_WINDOW`）ごとに、要るだけ前から
読んで掛け、掛け終えた区切りを覚えて、再生の塊はそこから切り出す（`engine/audio/mixer.py`
の `_window`） 元の音は前に読んだ所の続きだけを読み足す（`_raw_range`）
前は再生の塊（1024）ごとに前の音を読み直していて、AAC の素材では読み直すたびに解き直しに
なり 1 塊 19ms（予算 21ms）掛かって再生がブチブチ途切れ、読み直した所の音も塊ごとにわずかに
ずれて境目に段差が出た（利用者の手元） 今は平均 1.1ms、区切りの頭の塊で 16ms まで
区切りの位置は頼まれ方に依らないので、再生と書き出しは 1 標本も違わない
値は区切りの頭の値で掛ける（0.34 秒ごと） クリップの終わりより後ろの響きは鳴らさない

読む長さは値から決める ディレイは量を含めて -60 dB より大きいやまびこをすべて数え（波形の
表示と同じ決まり）、最も長い 2000ms・90%・量 100% で 66 回 132 秒 前は 10 秒と 50 回で切って
いて、10 秒を過ぎてもまだ元の 6 割で聞こえるやまびこが途切れた（PR #231） 何本も積んだときの
歯止めは `MAX_HISTORY_SECONDS`（300 秒） 長く読んでも間に合うように、前のエフェクトは後ろの
エフェクトが読む所から先だけに掛け（`_apply_effects` の `needs`）、ディレイは残す所にだけ足し
（`AudioContext.keep_from`）、元の音は同じ中身を 2 つ並べた輪（`_Tape`）へ書き足して全体を
写さない 132 秒の設定で音量調整を前に積んだとき、区切りの頭の塊で 19ms・平均 1.1ms
（予算 21ms） 輪は今持っている分から始めて足りなくなったら倍に広げ（値で決まる長さが上限）、
持つ長さが大きく縮んだら取り直す 最初から最大で取ると、クリップの頭を鳴らすだけで 100 MB を
持った（PR #231） 132 秒ぶんを本当に読む所では 2 つ持つので 100 MB ほど使う 入れ物の合計は
`RAW_BUDGET_BYTES`（256 MB 最も長いやまびこ 2 本ぶん）までで、越えたら最近使っていない物から
捨て、次に要るときに読み直す 値の動くクリップの読み戻しはクリップ全体で最も長い所にそろえる
（区切りごとに伸びると、伸びた区切りで前の音を頭から読み直して 90ms 掛かった）
貯めた区切りと元の音は、クリップが同じ物かに加えて、置いたシーンのクリップなら参照する
シーン（入れ子の先まで）が同じ物かで見分ける 外側のクリップだけで見ると、シーンの中を直しても
前の音を鳴らし続けた（PR #231）

キーフレームで動く値は、既定で区切りの中でもつなぐ（`Preferences.smooth_audio_motion`
`表示 → 設定…` 書き出しにも同じ値を渡す） 区切りの頭の値の音と終わり（次の区切りの頭）の値の
音を作り、区切りの中で少しずつ移す 頭の値だけでは動きが最大 0.34 秒遅れて段になった（PR #231）
値の動く区切りだけ 2 度掛けるが、リバーブは元の音の FFT を使い回し（`AudioContext.shared`）、
残る所だけを輪で畳み込む（overlap-save）ので、音量調整の後ろに積んだ 10 秒の測りで 99% の塊が
予算の中（リバーブの長さ 1.5→5 秒 平均 1.3ms・p99 21ms ディレイ 2000/90 で 19ms 音程で 7ms）
リバーブの長さは 0.1 秒刻みに丸め、響きの雑音は 1 度だけ引いて切り出す（刻みが変わる塊だけ
30ms ほど掛かるのは、つながない設定でも同じ） 切ると区切りの頭の値で掛ける（遅い機械向け）

## 5. 互換層は実物で確かめる


AviUtl / YMM4 の読み込みは、**実際に配布されているファイルを通すまで完成としない**

形式の推測だけで書いた YMM4 の読み手は、実物では 1 本も読めなかった
（`.ymmt` が ZIP だと知らず、素の JSON として開いて落ちた） AviUtl でも同じことが
起きている 資料と現物は食い違う

手順:

1. 実際に配布されているものを手に入れる
2. 片端から通し、記録された未対応を**数える**
3. **回数の多い順に**埋める 全部は埋めない

未対応は握り潰さず `CompatibilityReport` に残す ソフト内の
〔互換〕→〔互換性レポート…〕で一覧できる

**配布物そのものはリポジトリに入れない** 作者ごとに再配布の条件が違う
（例外は `licenses/` の使用許諾の全文と写し 配る zip に一緒に入れなければならない
物で、どれも原文のまま写してよいと書かれている 取得元と版は `THIRD_PARTY_NOTICES.md`、
GNU の全文は FSF の配る物と sha256 が同じことを試験で確かめている）
`tests/fixtures/ymm4` に置けばテストが拾い、無ければ飛ばす

### 混合の方式で読み込む

混合の方式（`layer_mode` が `mixed`）のプロジェクトでは、YMM4 と AviUtl のレイヤー番号を
そのまま混合トラックの並びにする（`compat/layers.py`） どちらもレイヤー 1 が一番奥で、
こちらの混合トラックと向きが同じ 動画アイテムは分けずに 1 本のクリップで絵と音を持ち、
鳴らす音は `AudioTrackIndex` で選ぶ AviUtl の 動画ファイル は音を持たせず、音声ファイル は
絵を隠して置く（AviUtl は同じ動画の音を 音声ファイル として別に書くので、二重に鳴らさない）

実物の配布物を両方の方式で置いて描き比べる試験がある（`tests/compat/test_real_mixed_layers.py`）
2026-09-24 に 500 本（中身を置ける 409 本・4 枚ずつ 1636 枚・音の鳴る物 2 本）を比べ、
1 画素・1 標本も違わなかった 配布物 230 本の `AudioTrackIndex` はどれも 0、AviUtl の
270 本はどれも 1 ファイル 1 オブジェクトで、同じ動画の 動画ファイル と 音声ファイル の組は
無かった 組を 1 本にまとめる所は、組の実物が来てから決める

### 値の意味は本体に描かせて読む

JSON のキーの名前から意味を推し量ると必ず外れる（`InOutZoom` の `Value` は
「縮める量」ではなく「隠れたときの大きさ」だった） 2 つの道具でそれを潰す

- `tools/ymm4_probes.py` … 値を 1 つずつ変えたテンプレートを作る
  （`第 1〜9 弾` を引数で選ぶ: `first` `second` `third` `fourth` `fifth` `sixth` `seventh` `eighth` `ninth`）
- `tools/ymm4_compare.py` … テンプレートを時間差で並べた `.ymmp` を作り（`build`）、
  YMM4 が書き出した動画と Sashimono の絵をフレームごとに比べる（`compare`）

```
.venv\Scripts\python.exe tools\ymm4_probes.py .work\probe5\probes.ymmt fifth
.venv\Scripts\python.exe tools\ymm4_compare.py --work .work\probe5 build .work\probe5\probes.ymmt
:: YMM4 で .work\probe5\compare.ymmp を開き、.work\probe5\ymm4.mp4 へ書き出す
.venv\Scripts\python.exe tools\ymm4_compare.py --work .work\probe5 compare
```

`compare` は `report.html` と、`ymm4 | Sashimono | 差` を並べた画像を `images/` に書く
差は 480x270 に縮めた平均なので、細い縁の違いは数に出にくい 数字だけでなく絵も見る

細い縁の違いを数に出すため、差の隣に 2 つの列を並べる（#200 一覧と `report.json` と
画面の両方 画面には「縁の差の大きい順」も出す）

| 列 | 測り方 | 読み方 |
| --- | --- | --- |

#### 縁の差の上限

キャラクターの動きのテンプレートは、縁の差の上限も `tools/ymm4_compare_edge_ceilings.json`
に持つ 縮めた平均は動きが数画素ずれても 0.5 ほどにしかならないので、ずれが戻っても
気付けない 値は既定の 3 枚で測った縁の差に 5 を足したもの 乱数で揺らす物も今の値で
見張る（大きく悪くならないため） 超えたら `compare` は終了コード 1
`--write-ceilings` は、このファイルに書いてあるテンプレートだけを書き換える
測ったすべてを足すと、縁が合わないと分かっている物まで見張りに入る

前の枠の絵が残りうる所は比べない（`shadowed_until`） テンプレートを並べる間の空きは
6 フレームで、残像（`AfterImageEffect`）のようにアイテムが終わった後も YMM4 の絵が残る
ものは、`build` がその後ろを `LINGER`（30 フレーム）だけ広げる 前に作った並びの書き出し
でも比べられるように、`compare` は前のテンプレートのアイテムの終わり（残像ならさらに
30 フレーム後ろ）より前を次の枠から外す 枠のすべてが隠れたテンプレートは数えて出し、
上限を持つ物なら終了コード 1

既定ではテンプレート 1 本につき 3 枚だけを比べる `--every` を付けると枠のフレームを
すべて比べ、1 本ごとに一番大きい差の 1 枚を出す 場面の切れ目のように一瞬だけずれる所は
3 枚では見落とす

YMM4 の書き出しは、最初の 1 枚の時刻が 0 ではなく 1 フレーム後ろから始まる 道具は
動画の頭の時刻を引いてそろえている 自前で書き出しを読むときも同じようにしないと、
YMM4 の絵が 1 枚遅れて並び、動きのある所で差が 8〜24 跳ねる

### 音を測る

`build` と `compare` は絵しか見ない 音（音量の曲線・定位の向き・再生速度 0 の意味）は
別の 2 つの副命令で測る

```
.venv\Scripts\python.exe tools\ymm4_compare.py --work .work\ymm4-audio audio-build
:: YMM4 で .work\ymm4-audio\audio-probe.ymmp を開き、audio-probe.mp4 へ書き出す
.venv\Scripts\python.exe tools\ymm4_compare.py --work .work\ymm4-audio audio-measure
```

`audio-build` は 440Hz の正弦波（ffmpeg で作る）を条件ごとの枠に並べた `.ymmp` と、
枠の一覧 `audio-probe.json` を書く 枠どうしは無音の間を空けて重ねない
`audio-measure` は書き出した音を枠ごとに左右別で測り、基準の枠（`Volume` 100・
`Pan` 0・`PlaybackRate` 100）に対する比を表にして `audio-report.json` へ書く
音量の表には「振幅比ならこの値・二乗ならこの値・dB 目盛りならこの値」を並べる
どれに近いかは人が読んで決める

`Pan` の値域は -100〜100 とした 実物の音声アイテム 125 個はすべて 0 で実物からは
決められないが、YMM4 本体（4.48.0.3）の IL に `Animation(0, -100, 100)` を作る並びが
18 か所あり、`Animation(0, -1, 1)` は 1 か所も無い もし値域が -1〜1 なら YMM4 が
読み込みで丸めるので、表の `Pan=-100` と `Pan=-50` が同じ値になる そうなっていたら
この判断が外れている

2026-09-23 に YMM4 4.56.1.1 で測った結果（440Hz の正弦波 14 枠 基準の枠との比 最大振幅）

| 項目 | 実測 | 読み |
|---|---|---|
| `Volume` | 0→0.000 / 10→0.100 / 25→0.250 / 50→0.501 / 75→0.751 / 90→0.901 | 振幅比そのまま |
| `Pan` | -100→左 1.00 右 0.00 / -50→左 1.00 右 0.50 / 50→左 0.50 右 1.00 / 100→左 0.00 右 1.00 | 負が左 近い側はそのまま 遠い側だけ直線で下がる |
| `PlaybackRate` | 0→無音・長さ 0 / 50→3.98 秒・220Hz / 200→1.00 秒・880Hz | 0 は鳴らない 速さと一緒に高さも変わる 最大振幅は変わらない |

`Pan=-100` と `Pan=-50` は別の値になったので、上の値域の判断は合っていた
読み込み（`compat/ymm4/template.py` の `_audio_effects` と `_playback_rate`）はこの表で
写し方を決めた `Volume` と `Pan` は `audio_volume` の `volume` と `pan`（同じ作り）へ、
`PlaybackRate` はクリップの `speed` へ `rate / 100` で写す `Length` はタイムライン上の
長さのままで、素材は `Length × rate` だけ進む（50% で 2 秒の素材が 3.98 秒鳴った）
0 は `speed` に置けない（正の数だけ）ので、音量 0 にして鳴らさない
動画アイテムでは `speed` が映像のクリップにも効く 絵の速さは下の「絵の速さを測る」で
確かめ、0 以外は YMM4 と一致した 0 は YMM4 が素材の頭の絵で止めるので、クリップの
`hold_at`（絵を止める素材の時刻）を `source_in` にして止める（#115）
新しい版の書き出しは動く値の `PlaybackRate2` と `PlaybackRateAudioProcessingMode` も持つ
実物はどれも `PlaybackRate` と同じ値・`Resampling` だった どちらが効くのかは、下の
「`PlaybackRate` と `PlaybackRate2` の食い違い」で測った

### 絵の速さを測る

動画アイテムの `PlaybackRate` が絵をどう進めるか（とくに 0 で止まるのか）を測る

```
.venv\Scripts\python.exe tools\ymm4_compare.py --work .work\ymm4-video-rate video-rate-build
:: YMM4 で .work\ymm4-video-rate\video-rate-probe.ymmp を開き、video-rate-probe.mp4 へ書き出す
.venv\Scripts\python.exe tools\ymm4_compare.py --work .work\ymm4-video-rate video-rate-measure
```

`video-rate-build` は ffmpeg の testsrc2 で 4 秒の動画（全フレームが鍵フレーム）を作り、
`PlaybackRate` を 100・50・200・0 にした動画アイテムを 6 秒ずつの枠に並べる
ffmpeg や libx264 が無ければ理由を言って終える
`video-rate-measure` は書き出しの各フレームを素材の全フレームと比べて一番近い物の番号を取り、
枠の頭からの経過フレームに対する傾き（1 で等倍・0.5・2・0 で止まる）を表にする
同じ `.ymmp` を Sashimono でも描いて並べる（`--skip-sashimono` で飛ばせる）

2026-09-23 に YMM4 4.56.1.1 で測った結果（素材 4 秒・枠 6 秒）

Sashimono の列は、止めた絵を写す前（#114 の時点）と、写した後（#115）の 2 つ
#115 の列は、同じ YMM4 の書き出しに対して Sashimono 側だけを描き直して測った

| 枠 | YMM4 | Sashimono（#114） | Sashimono（#115） |
|---|---|---|---|
| `PlaybackRate` 100 | 1.00 倍 頭 0 一致 180 | 1.00 倍 頭 0 一致 120 | 1.00 倍 頭 0 一致 180 |
| `PlaybackRate` 50 | 0.50 倍 頭 0 一致 180 | 0.50 倍 頭 0 一致 180 | 0.50 倍 頭 0 一致 180 |
| `PlaybackRate` 200 | 2.00 倍 頭 0 一致 180 | 2.00 倍 頭 0 一致 60 | 2.00 倍 頭 0 一致 180 |
| `PlaybackRate` 0 | 止まる 頭 0 一致 180 | 1.00 倍 頭 0 一致 120 | 止まる 頭 0 一致 180 |

#115 の後は、4 つの枠の 720 フレームすべてで、YMM4 と Sashimono が素材の同じフレームを出した

0 以外の速さは一致した 0 は YMM4 が素材の頭の絵で止め、そのころの Sashimono は等倍で
動いていた 一致数の違いは速さとは別の話で、素材より枠が長いとき、YMM4 は最後の絵で止めて
出し続け、Sashimono は素材が終わると何も出さなかったことから来る

同じ日に 2 つの止まり方を確かめた

- **素材より長い動画アイテム** 素材 120 フレーム・枠 180 フレームで、0→119 のあと 119 が
  60 回 頭へ戻って繰り返さない（`IsLooped` が立っていないとき）
- **`PlaybackRate` 0** 枠の 180 フレームすべてが素材の 0 フレーム目（`ContentOffset` の位置）

写し方（#115）

- クリップに `hold_at`（絵を止める素材の時刻 秒）を持たせた 絵を取る時刻が
  これを越えたら、ここの絵を出し続ける 描画・並列デコードの先読み・タイムラインの絵の並びは
  同じ `Clip.picture_time` で時刻を決めるので、止めた後の時刻をデコードしに行かない
- 「クリップの中の経過」ではなく素材の中の時刻で持つ 分割・トリム・速さの変更・無音のカットで
  `source_in` と `speed` が変わっても、値を写すだけで同じ絵が出る 分割した後半が止める時刻より
  後から始まれば、後半はずっと止まった絵になる
- 音には効かない 素材の終わりの後は素材が無いので無音、`PlaybackRate` 0 は音量 0 で鳴らさない
- `PlaybackRate` 0 の動画アイテムは `hold_at` を `source_in` にする
- 素材より長い動画アイテムは、置くときに素材を読んで長さが分かってから、
  `Length × PlaybackRate` が素材の残り（映像の終わり − `ContentOffset`）より長ければ、
  `hold_at` を映像の終わりの time_base 1 刻み手前にする デコーダはその時刻を越えない
  最後のフレームを出すので、可変フレームレートでも最後のフレームになる（平均の 1 フレーム
  ぶん引くと、最後の間隔が短い素材で 1 つ前の絵になる）
  映像の終わりは映像の道の長さ（`VideoStreamInfo.end_time` 素材を読むときに取る）で見る
  素材の頭から数えた時刻で、`source_in` やデコーダが読む時刻と同じ数え方（下の「素材の中の
  時刻は頭から数える」） コンテナの長さは、音の方が長い素材では最後の映像フレームより後ろも
  指すので混ぜない 道の長さが分からない素材（前に取り込んだ物）はコンテナの長さで見る
  デコーダが絵を出すのも映像の道の終わりまでにした（道の長さが分からない素材は素材全体の長さ）
  音の方が長い素材は、それまで音だけの区間にも最後の絵が
  出ていたが、いまは何も出さない 最後の絵を出し続けたいクリップは `hold_at` で止める
  長さの分からない素材・静止画・`IsLooped` の物は止めない（繰り返しは互換性レポートに数えて残す）
- 保存形式の版を 4 に上げた 3 までの本体は項目を知らず、止めた絵が動き出すうえ保存し直すと
  消える 3 までのファイルは止めないクリップとして開く

### 素材の中の時刻は頭から数える

分割して書き出した物（`ffmpeg -output_ts_offset`）や放送の録画（MPEG-TS）は、最初の
フレームの PTS が 0 より後ろにある PTS そのままで素材の時刻を数えていたころは、置いた
クリップ（`source_in` 0・長さは素材の長さ）が読む時刻がすべて最初のフレームより前になり、
頭の絵が止まったまま動かず、音はクリップの外にあって鳴らなかった（Issue #123）

- 素材の中の時刻（`source_in`・`hold_at`・`VideoStreamInfo.end_time`・`MediaItem.duration`・
  サムネイルと波形）は、PTS から素材の原点（`engine/decode/probe.py` の `media_origin`）を
  引いて数える クリップの `source_in` は画面でも素材の頭からの位置として扱っている
- 原点は素材 1 本に 1 つ 映像と音声のデコーダが同じ値を引くので、素材の中の映像と音の
  食い違いはそのまま残る
- 原点は最初の映像ストリームの頭（映像が無ければ音声の頭の最小） コンテナの頭（全ストリーム
  の最小）にしないのは、AAC の前置き（プライミング）が映像より 20ms ほど早く始まる素材が
  多いため コンテナの頭を原点にすると、映像のフレームの時刻がすべてその分だけ後ろへずれ、
  フレームの境目の時刻で 1 つ前の絵が出る 前置きは復号すると捨てる区間なので、原点より前
  （負の時刻）へ出してよい 控え（プロキシ）は映像だけを写して PTS をそのまま持つので、
  原点を映像の頭にしておけば元の素材と同じ時刻になる
- 頭が負の素材は原点を 0 にする 前から 0 を原点にして正しく映っていた素材で、引くと動く
- 頭が少しだけ後ろの素材も動く ffmpeg で焼いた MP3 は頭が 0.025 秒（符号化の遅れを
  飛ばした後の最初のサンプル）で、前はクリップの頭に 25ms の無音が入っていた いまは
  頭から鳴るので、前に作ったプロジェクトの MP3 の音は 25ms 早く鳴る MPEG-TS（手元で
  焼いた物は頭が 1.42 秒）は前は頭の絵が止まったままだった
- 素材の長さ（`MediaItem.duration`）は原点から終わりまで 前置きの分を含めると、置いた
  クリップが 1 フレーム長くなり、最後の 1 フレームが何も映らない
- サムネイルのシート（版 3）と波形（版 2）は版を上げた 前の版は頭が 0 より後ろの素材で
  最初の絵ばかり・無音の波形になっていて、上げないとそれが残る 控えは PTS をそのまま
  写しているので作り直さなくてよい
- 保存形式の版を 5 に上げた 版 4 の `end_time` は PTS そのままの値なので、読むときに捨てて
  映像の終わりを覚える前の素材と同じ扱いにする（絵を止める所で素材を開き直す）
  `source_in` と `hold_at` はそのまま読む 頭が 0 の素材は何も変わらない 頭が 0 より後ろの
  素材で、手で素材の中の位置を頭の時刻ぶん後ろへずらして映るようにしていたクリップは、
  5 で開くとその分だけ後ろを読む 見分けるには素材を開く必要があり、コア層では開けない
- 字幕起こし（faster-whisper）はパスを渡すと音声の最初のサンプルを 0 秒として数え、音の頭が
  原点と違う素材（前置きの分など）で起こした字幕がその差だけずれた（#125） 音は Sashimono の
  音声デコーダで原点から 16kHz・モノラルに読み、配列で渡す（`asr/whisper.py` の `_media_audio`）

2026-09-23 に YMM4 4.56.1.1 で `ContentOffset` の数え方を測った 素材は `video-rate-build` と
同じ testsrc2（4 秒・全フレームが鍵フレーム）と、それを `-c copy -output_ts_offset 5` で
頭 5 秒にした物、さらに映像だけ `-itsoffset 0.5` で遅らせて音を足し、頭 5 秒にした物
（音の頭 4.978 秒・映像の頭 5.5 秒）の 3 本 それぞれ `ContentOffset` 0 と 1 秒の動画アイテムを
並べて `tools/ymm4_export.py` で書き出し、`ymm4_compare.py` の突き合わせ（`match_frames`）で
各フレームが素材の何フレーム目かを読んだ

| 素材 | `ContentOffset` 0 | `ContentOffset` 1 秒 |
|---|---|---|
| 頭 0 | 0・1・2… | 30・31・32… |
| 頭 5 秒 | 0・1・2… | 30・31・32… |
| 音が映像より 0.52 秒早い（頭 5 秒） | 0・1・2… | 30・31・32… |

YMM4 は `ContentOffset` を素材の頭から数え、音が映像より早く始まる素材でも映像の頭を 0 に
する（コンテナの頭を原点にしていれば、頭の 15 フレームほどは素材の絵が出ない） Sashimono も
6 枠すべてで同じフレームを出した 音の側（音が早い素材で YMM4 が音をどこに置くか）は測っていない

### `PlaybackRate` と `PlaybackRate2` の食い違い

新しい版の `PlaybackRate2`（動く値）と `PlaybackRateAudioProcessingMode` がどう効くかを
測る（Issue #117） 上の 2 つの探り（`video-rate-build` と `audio-build`）は、前からある枠の
後ろに、2 つをわざと食い違わせた枠を持つ 前からある枠は形も位置も変えていないので、
前の測り結果とそのまま比べられる

`PlaybackRateAudioProcessingMode` の取りうる値は実物に `Resampling` しか無かったので、
YMM4 本体（4.56.1.1）の `YukkuriMovieMaker.dll` のメタデータの表から列挙
`YukkuriMovieMaker.Project.Items.PlaybackRateAudioProcessingMode` を読んだ
`Resampling = 0` と `Sola = 1` の 2 つだけ

`video-rate-measure` は 30 フレームごとに傾きを区切って出し、`PlaybackRate` の値が効いた
ときと `PlaybackRate2` の値が効いたときの予想と並べて、近い方を書く `audio-measure` は
鳴っている長さと中心の周波数で同じように読む（`Sola` の枠は高さを保つかどうか）

2026-09-23 に YMM4 4.56.1.1 で測った結果（書き出しは `tools/ymm4_export.py` で自動）

| 枠 | 絵（30 フレームごとの傾き） | 音（長さ・中心の周波数） | 効いた値 |
|---|---|---|---|
| `PlaybackRate` 100 / `PlaybackRate2` 50 | 1.00・1.00・1.00・1.00 | 2.00 秒・440Hz | `PlaybackRate` |
| `PlaybackRate` 50 / `PlaybackRate2` 100 | 0.50 が 6 区間 | 3.98 秒・220Hz | `PlaybackRate` |
| `PlaybackRate` 100 / `PlaybackRate2` 50→200 | 1.06・1.25・1.41・1.50 | （測っていない） | どちらとも合わない |
| `PlaybackRate` 50 / `Sola` | - | 3.97 秒・440Hz | 高さを保つ |
| `PlaybackRate` 200 / `Sola` | - | 1.00 秒・440Hz | 高さを保つ |

止まった値が食い違うときは、絵も音も `PlaybackRate` が効いた 読み込み
（`compat/ymm4/template.py` の `_playback_rate`）は `PlaybackRate` を読み、食い違いは数えない

`PlaybackRate2` を動かした枠は、`PlaybackRate` の 100 一定とも、`PlaybackRate2` の
50→200 とも合わなかった 頭の値を `PlaybackRate`（100）・終わりの値を `PlaybackRate2` の
最後（200）とした直線なら、各 30 フレームの予想は 1.08・1.25・1.42・(1.58) になり、
はじめの 3 区間が ±0.01 で合う（4 つ目は素材を読み切る所にかかる） **1 つの枠からの読み
なので決め打ちしない** `video-rate-measure` はこの読みも 3 つ目の予想として並べるので、
次に別の値で測るときに合うかを確かめる こちらの `speed` は動かせないので、読み込みは
頭の値（`PlaybackRate`）で置き、動く速さは写せないと互換性レポートに数えて残す

`Sola` は長さだけを速さどおりに変え、高さを保った（WSOLA のような変え方） こちらの
`speed` はミキサーの線形の並べ直しで、高さを保つ変え方を持たない 読み込みは長さを
`speed` で合わせ、高さも変わることを数えて残す（等倍と 0 は高さが変わらないので数えない）
`Resampling` と `Sola` 以外の値は、まだ見ていない変え方として数えて残す

YMM4 が読み込みで断った設定（列挙型の名前の間違いなど）は、ダイアログが別の窓に
隠れて見えないことがある そのときは YMM4 を前に出して Ctrl+C を押すと、
エラーの文面がクリップボードに入る

YMM4 と違い（縦に長く切れる）、正しい大きさにしたことで違う形が大きく出た

### YMM4 の書き出しを道具に任せる

上の探りの「YMM4 で開いて書き出す」所は、`tools/ymm4_export.py` に任せられる
YMM4 の画面を UI Automation で操作して、開く・〔ファイル(F)〕→〔動画出力〕・〔出力〕・
保存の名前を入れる・書き終わりを待つ・閉じる、までを行う（Issue #116）
各 `*-build` は書き出す命令も並べて出す

```
.venv\Scripts\python.exe tools\ymm4_compare.py --work .work\ymm4-audio audio-build
.venv\Scripts\python.exe tools\ymm4_export.py --project .work\ymm4-audio\audio-probe.ymmp --output .work\ymm4-audio\audio-probe.mp4 --no-compressor
.venv\Scripts\python.exe tools\ymm4_compare.py --work .work\ymm4-audio audio-measure
```

**動かしている間は YMM4 の窓が前に出て、マウスとキーボードを取り合う** 本人の PC で
走らせるときは、必ず本人に断ってからにする 途中でクリックや打鍵が混ざると、別の欄へ
書いたり別の物を押したりする

- YMM4 が既に開いていれば何もせずに終了コード 1 で止まる 作業中のプロジェクトの上から
  別のプロジェクトを開かないため
- YMM4 の場所は `--ymm4` → 環境変数 `YMM4_EXE` → `.ymmp` の関連付け → よく見る置き場
  （`C:\` `D:\` 直下や `Program` の下の `YukkuriMovieMaker_v4` など）の順に探す
  名指しした場所に無ければほかを探さずに止まる 見つからなければ探した所を並べて 1 で止まる
- 書き出しは同じ置き場の一時の名前（`<出力の名前>.sashimono-<16 進 8 桁>.part.mp4`）へ行い、
  書き終えたと確かめてから出力の名前へ置き換える 途中で失敗したらその回の一時の方を消し、
  前の書き出しはそのまま残る 印は毎回変え、既にあるファイルと重ならない名前を選ぶ
  元からあるファイルは道具が作った物か分からないので、始めに何かを消すことはしない
  拡張子を mp4 のままにするのは、保存の窓の種類（mp4）と食い違わせないため
  PowerShell ごと止めたときなどは一時のファイルが残ることがある `.sashimono-` と 8 桁の
  印が入り `.part.mp4` で終わる名前がそれなので、書き終えていない物として消してよい
- 書き終えたのに出力の名前へ置き換えられなかったとき（出力の動画をプレーヤーが開いている
  など）は、書き上がった物を `<出力の名前>.sashimono-<16 進 8 桁>.done.mp4` へ名前を変えて
  残し、場所を知らせる `.done.mp4` は書き上がった物なので、出力の名前へ手で置き換える
  名前で分けたのは、道具の出力を見返さなくても、あとで見つけた人が見分けられるようにするため
- 出力の名前が既にあるフォルダ（名前が `.mp4` で終わる）なら、YMM4 を起こす前に止まる
- 操作して閉じるのは、道具が起動した process の窓だけ 動かしている間に本人が別の YMM4 を
  開いても触らない 起動した process が主の窓を出さずに終わったら、推測でほかの窓を触らずに止まる
- `--no-compressor` は〔音量調整 / 音割れ対策（コンプレッサー）〕を「音量調整しない」
  「圧縮しない」にしてから書き出す 既定の「自動」「最大音量を0dB以下にする」のままだと
  音量の比が潰れるので、**音の探りでは必ず付ける** 終わったら成功でも失敗でも元の値へ
  戻し、書き出しの窓を開き直して戻ったことを確かめる 戻せなかったら `!!!` で囲んで知らせ、
  終了コード 2 で終わる そのときは書き出しの窓で手で戻す
- 書き出しの解像度・fps・範囲は YMM4 の書き出しの窓の今の設定のまま この道具は変えない
  絵の探り（1920x1080・30fps・頭から終わりまで）で違う設定になっていたら、先に手で直す
- 書き終わりは、進み具合の窓が消えたあと、出力の大きさが 5 秒止まり、YMM4 がファイルを
  手放したことで決める 進み具合の窓が消えても書き出しが続いていたことがあった
- 書き終わりのあとに書き出しのコマ数を数え、プロジェクトの長さと比べる（Issue #210）
  YMM4 が途中で書くのを止めても、大きさが止まって手放されるので、上の決め方だけでは
  成功と言っていた 長さは選んでいるタイムラインの最後のアイテムの終わり（`Frame + Length`
  の最大）で、タイムラインの `Length` ではない 手元の実物の書き出し 20 本はどれもアイテムの
  終わりちょうどのコマ数で、`Length` より 6〜30 少なかった 書き出しの fps が違えば時間で揃え、
  要るコマ数は切り上げる 数えるのは復号できたコマで、目次（moov）のコマ数は信じない
  足りなければ `!!!` で囲んで、何コマ書けたか・プロジェクトの何フレーム目（何分何秒）で
  止まったかを出し、終了コード 1 で終わる 開けない動画も同じく失敗にする 途中までの動画と
  開けない動画は
  `<出力の名前>.sashimono-<16 進 8 桁>.short.mp4` へ退ける 出力の名前のまま残すと measure が
  途中で切れた物を測るため 前の書き出しは PowerShell が置き換えた時点で無くなっている
  長さを読めないプロジェクト（アイテムが無いなど）は、YMM4 を起こす前に止まる
- `--timeout`（既定 1800 秒）で書き出しを待つ長さを変えられる

画面の操作は `tools/ymm4_export.ps1`（Windows PowerShell 5.1）が受け持つ UI Automation を
.NET からそのまま呼べるためで、Python で書くと `comtypes` などの依存が増える
このファイルは **BOM 付きの UTF-8** で置く BOM が無いと 5.1 は Shift_JIS として読み、
〔ファイル(F)〕も「名前を付けて保存」も見つからなくなる（試験で見ている） 手で直すときは
型の名前を Add-Type より前に書かないこと、変数名が大文字小文字を区別しないことにも気を付ける

### AviUtl2 の書き出しを道具に任せる

`tools/aviutl_compare.py` の「AviUtl2 で開いて書き出す」所は、`tools/aviutl2_export.py` に
任せられる（Issue #108） AviUtl2 を起動してプロジェクトを開き、〔ファイル〕→〔ファイル出力〕→
〔連番ファイル出力〕で**連番の PNG** を書き出し、閉じるまでを行う `compare` は作業フォルダの
`aviutl` フォルダに PNG があればそれを読む（無ければ今までどおり `aviutl.mp4`）

```
.venv\Scripts\python.exe tools\aviutl_tag_probes.py --work .work\composite-font
.venv\Scripts\python.exe tools\aviutl2_export.py --project .work\composite-font\compare.aup2 --output .work\composite-font\aviutl --aviutl2 J:\aviutl2_v2.1.6a\aviutl2.exe
.venv\Scripts\python.exe tools\aviutl_compare.py --work .work\composite-font compare
```

**動かしている間は AviUtl2 の窓が前に出る** 本人の PC で走らせるときは、必ず本人に断ってからにする

- PNG にしたのは、動画を通すと鮮やかな色が痩せ、字の端がにじむため 基準線や行の高さの
  1 画素の違いを測れる 書き出しの設定（PNG の透明色・JPEG の品質）は変えない
  透明色ありで書き出した PNG は、比べるときに黒の上へ重ねる
- AviUtl2 のメニューは Win32 の普通のメニューで、UI Automation には出てこない
  メニューの名前をたどって番号を引き、主の窓へ `WM_COMMAND` を送る 番号はプラグインの
  並びで変わるので決め打ちしない 保存の窓は古い形で、名前の欄（1148）へ `WM_SETTEXT` で
  書いて読み返し、〔保存〕を押す 押すのは `PostMessage` 書き出しは押下の中で進むので、
  `SendMessage` だと書き終えるまで返らない
- AviUtl2 か YMM4 が開いていれば何もせずに 1 で止まる 場所は `--aviutl2` → 環境変数
  `AVIUTL2_EXE` → `.aup2` の関連付けの順 当て推量では探さない
- 書き出しは出力の隣の一時のフォルダ（`<出力>.sashimono-<16 進 8 桁>.part`）へ行い、
  プロジェクトの最後のオブジェクトの終わりまでの枚数が揃い、最後の 1 枚が手放されてから
  出力の名前へ変える 出力が空でないフォルダなら書き出す前に断る 失敗したら一時の方を消す
  PowerShell が書き終えたと言っても、入口が一時のフォルダの PNG を数え直し、枚数が違えば
  `書き出しが途中で止まりました <書けた数> / <見込み> 枚` と出して 1 で終わる（Issue #210）
- **AviUtl2 は閉じるときに設定を書き直す**（`aviutl2.ini` の保存の窓の置き場、`history.ini`
  の開いた履歴、`explorer.ini`） 起動する前に中身の控えを取り、閉じたあとに元の中身へ
  戻して読み返す 戻せなかったら `!!!` で知らせて 2 で終わる AviUtl2 が閉じなかったときも
  戻さずに 2 で終わる（開いたまま戻すと、閉じるときにまた書き直される） 置き場は本体の
  隣に `data` があればそこ、無ければ `%PROGRAMDATA%\aviutl2`
- 閉じるときに AviUtl2 が自分で足す自動控え（`Backup\AutoBackup_*.aup2`）は、本人の控えと
  同じ置き場なので消さない 増えた物の名前を出す
- 画面の操作は `tools/aviutl2_export.ps1` が受け持つ YMM4 の物と同じく **BOM 付きの UTF-8**
- 書き出しが 5 分に満たなければ、AviUtl2 の自動控えは増えも減りもしなかった（2026-09-25 3 回）

### 拡大率とクリッピングを AviUtl2 で測る

`tools/aviutl_scale_probes.py` は白い四角と単色の画像に、描画設定の拡大率・縦横比、`拡大率` と
`リサイズ` の X Y、`クリッピング`（中心の位置を変更 も）を掛けた見本を並べ、`measure` で AviUtl2 の
書き出しと Sashimono の白の外形を並べて出す（Issue #167） 測った数は
`tests/compat/test_aviutl_measured.py` が持つ

```
.venv\Scripts\python.exe tools\aviutl_scale_probes.py --work .work\aviutl-scale build
.venv\Scripts\python.exe tools\aviutl2_export.py --project .work\aviutl-scale\compare.aup2 --output .work\aviutl-scale\aviutl --aviutl2 J:\aviutl2_v2.1.6a\aviutl2.exe
.venv\Scripts\python.exe tools\aviutl_scale_probes.py --work .work\aviutl-scale measure
```

- 拡大率は横と縦に 1 回ずつ掛かる 変形の `scale_y` は `scale` に重ねて掛かる縦の比なので、
  拡大率を両方へ入れていた読み込みは縦にだけ 2 回掛けていた（200 の 200x200 が 400x800）
- 縦横比は正で横を、負で縦を縮める（50 で 100x200、-50 で 200x100）
- `拡大率` と `リサイズ` の X Y は軸ごとの拡大率（拡大率 150・X 200・Y 50 で 600x150） Z は板の
  絵に効かないので 100 のままなら読んだことにする
- `クリッピング` は絵の置かれた範囲の端から数える（#174 の直しが AviUtl2 でも合った） 中心の
  位置を変更 は残りの真ん中を元の中心へ戻す（右 − 左 の半分だけ右、下 − 上 の半分だけ下）
- 16 本すべてが外形の端 1 画素以内で合った `aviutl_compare.py` の `compare` と `preview` も
  素材を登録してから置くようにした 画像の見本がこれまで真っ黒で比べられていた

### 乱数ものは画素ではなく統計で合わせる

集中線・パーティクル・ノイズ・星空・グリッチのように**乱数を使う効果**は、
本体と 1 画素まで同じ絵には**ならない** 本体の乱数の作り方（どの種から、どの
混ぜ方で）は公開されておらず、推測で書けば必ず外れる ここは合わせにいかない

#### 何をもって「合った」と見なすか

星空（Issue #45）で取ったやり方をそのまま基準にする 実物に描かせた動画から
**数えられる量**を拾い、こちらの絵の同じ量と突き合わせる

| 見る量 | 例（星空で実際に測ったもの） |
|---|---|
| 個数 | 設定の粒の数ぶんが画面に居る（透明になった粒だけ外す） |
| 分布 | 粒が画面の全体に散る 向きや位置が片側へ偏らない |
| 速さ | 1 フレームあたりの広がりの**中央値** 速度 6 で 0.72%、12 で 1.46% |
| 明るさ | 線 1 枚ぶんの濃さ 集中線は 255 中の 67 ほどで、真っ白にはならない |
| 面積 | 画面のうち線が載っている割合 濃さ 40 で 18%、80 で約 65% |

合わせる量は**平均と散らばり**で見る 1 つ 1 つの粒や線がどこに来るかは見ない
ずれを許す幅は、実測を並べて決める（星空の速さは ±25%、集中線の面積は 1.5 倍
以上の差が付くか、という粗さで足りた）

#### 種の決め方

1. **同じフレームは何度描いても同じ絵になる** 描き直すたびに変わると、止めた
   プレビューでも絵がちらつき、書き出しとプレビューも一致しない
2. **保存して開き直しても変わらない** 種は「時刻」と「オブジェクトの持ち物」
   だけから作る 実行ごとの乱数（`random.random()` や種を与えない `default_rng`）は
   使わない
3. **版を上げても変わらない** 混ぜ方は自前で持つ `np.random` の `Generator` は
   版をまたいで同じ並びを出すと約束していない（凍結されているのは `RandomState`
   の方だけ） 集中線と星空は `engine/motion_shapes.py` の `unit_randoms` /
   `_rand`（splitmix64）を、シェーダは `PRELUDE` の `hash()` を使う
4. **引き直す区切りをはっきり決める** 毎フレーム引き直すのか、`間隔`／`切り替え`
   の回ごとなのか、1 周ごとなのかを式に書く 途中で引き直すと、流れていく粒が
   毎フレーム跳ぶ（星空は「周回が変わったときだけ置き直す」）
5. **用途ごとに列を分ける** 1 本の並びから順に取り出すと、途中で 1 つ取る・
   取らないが分かれたときに、その先の値が全部ずれる 向きと太さで別の列を使う

同じ設定のオブジェクトを 2 つ並べると、**同じ絵になる**（種が時刻だけで決まるため）
ずらしたいときは `シード` を持つ効果でその値を変える 本体の側にも種の設定が無い
効果（YMM4 の `RandomMoveEffect` などは JSON に種を持たない）は、こちらでも
足していない 足すと、読み込んだ値が本体と合っているかを確かめられなくなる

#### 比較の道具での読み方

`tools/aviutl_compare.py` / `tools/ymm4_compare.py` の `report.html` は、
**乱数ものでは画素の差が大きく出る**（集中線の 1 本 1 本が別の向きに走るので、
差の絵は全面が光る） ここは落第ではない 見るのは次の順

1. 差の絵の**形** 線の載る範囲・抜けた真ん中の大きさ・広がりの向きが合っているか
2. 2 枚の**明るさの平均**が近いか 平均が 2 倍違えば、本数か濃さの読み違い
3. 時間で変わるものは、**変わり方**が合っているか 切り替えの回数が違えば、
   `flicker`／`Span` の単位を読み違えている

画素の差の数字（`report.json` の平均差）は、乱数ものだけ別に見る 他の効果の
目安（差 8 以下）をそのまま当てると、直しようのない所で止まる

#### テストの書き方

- **決め打ちの画素で比べない** 「この座標が 255」は乱数の並びを凍らせるだけで、
  実物と合っているかを何も言わない
- 見るのは統計 `tests/engine/test_concentration.py` と
  `tests/engine/test_motion_shapes.py` の `TestStarField` が見本
  （割合・中央値・個数・相関）

  「線の並びが NumPy 由来だと版で変わる」のように、落ちたときに何が起きるかが
  分かる名前にする
- 上の 1〜3 の決まりは、決まりごとに試験を 1 本ずつ持つ 同じフレームを 2 度描いて
  一致するか、`np.random` を封じても描けるか、を直に確かめる

### DLL の中身は書き直さず、実物を呼ぶ

配布スクリプトの中には、処理を DLL（中身が DLL の ``.mod2``）へ切り出している物がある
（テレビ字幕の ``TVSubtitle.scan`` は、文字の絵から行ごとの四角を探す） DLL の中身は
公開されておらず、説明書きから書き直すと必ず外れる 実際に呼んで測ったら、1 文字ずつ
ではなく 1 行ずつの四角で、「接着間隔」は上下の行の隙間に効いていた

- **利用者の AviUtl2 に入っている DLL をそのまま呼ぶ**（``compat/aviutl/native.py``）
  呼び方は AviUtl ExEdit2 Plugin SDK の ``module2.h`` に従う（MIT ライセンス）
- DLL は Sashimono と同じ権限で動く（Lua の閉じ込めの外） 読むのはスクリプトフォルダに
  本人が置いた物だけにし、設定で切れるようにしてある
- 配布物の DLL はリポジトリに入れない 試験は、Python で作った関数を C の関数として
  渡し、DLL と同じ作法で引数を読み結果を積ませて確かめる 実物での確認は、DLL が
  入っている機械でだけ走る試験（無ければ飛ぶ）に分ける

### `obj.module` の相手は、ファイルとは限らない

**汎用プラグイン（`.aux2`）が名前を付けて登録したモジュール**がある
合成フォントの `obj.module("compositefont")` がそれで、`compositefont.mod2` という
ファイルはどこにも無い 名前でファイルを探すだけだと、永遠に見つからない

- 読む側は `compat/aviutl/plugin.py` 作法は SDK の `plugin2.h` に従う
  `InitializePlugin` → `RegisterPlugin(HOST_APP_TABLE*)` の順で呼び、プラグインが
  `register_script_module_name(表, 名前)` で登録してきた表を受け取る
  **`GetCommonPluginTable` は `InitializePlugin` より後**（実物はそうしないと初期化に失敗する）
- **読むのは、名前を出すと確かめたプラグインだけ**（`plugin.KNOWN_PROVIDERS`
  いまは `compositefont` → `comfont.aux2`） 何を登録するかは初期化するまで分からないので、
  前は `obj.module` が引かれるたびに `Plugin` フォルダの全部を初期化していた テレビ字幕
  （`TVSubtitle` は `.mod2` のファイル）を描くだけで WhisperAutoSub が Python を起動し、
  `Plugin\WhisperAutoSub\whisper_subtitle` の `whisper_subtitle.ini`・`temp\probe_env.py`・
  `whisper_debug.log` を書いていた（Issue #135） 表に無いプラグインのモジュールを使いたい人は
  `表示 → 設定…` の「AviUtl2 の汎用プラグインを全部読んで探す」で全部を読む作りへ戻せる
  （既定は切） 見つからなかった名前には、その設定で探せることを互換性レポートに残す
  表へ足すのは、実物を読んで登録を確かめた物だけ
- 試験は本人の `Plugin` フォルダを読まない `tests/conftest.py` が既定の置き場と
  プラグインへ渡す設定の置き場を一時フォルダへ向け、本物の置き場の DLL を読もうとしたら

### テキストの制御文字

AviUtl2 の組み方のテキスト（`layout` が `aviutl`）は、本文の `<@書体>` `<#色>` `<s大きさ>`
を読む（`compat/aviutl/text_tags.py` と `engine/sources.py` の `_aviutl_lines`）
YMM4 や Sashimono の文字は読まない 本文に `<@` と書いた人の字を消さないため
決まりは 2026-09-24 に AviUtl2 v2.1.6a に見本（`tools/aviutl_tag_probes.py`）を描かせて測った

| 見たこと | 決まり |
|---|---|
| `<@Meiryo>` `<@MS Gothic>` `<@Yu Mincho>` も設定欄の `フォント=Meiryo` も Yu Gothic UI で描かれた | 日本語の名前を持つ書体は日本語の名前（`メイリオ`）でしか見つからない 見つからなければ既定の Yu Gothic UI（設定欄の書体ではない） |
| 書体・大きさが混ざった行の字の下端がそろう | 1 本のベースラインに乗る |
| Arial・メイリオ・ＭＳ ゴシック・游明朝の行が上 99・下 61 の 160 | 行の高さとベースラインは、その行で**行送りのいちばん大きい書体 1 つ**で決まる（上の高さの最大と下の深さの最大を足すのではない） 行送りは #64 と同じ（上 + 下 + 行間の余白） |
| 行ごとに書体を変えた 3 行が 150 + 115 + 100 | 行の高さは行ごと |
| `H\n<s200>\nH` の真ん中の行が大きさ 200 の高さ | 文字の無い行は、その行の終わりの書体と大きさの行送り |
| `<@メイリオ>H\nHH<@>` の 2 行目もメイリオ | 切り替えは改行をまたいで続く |
| 入れ子の後の `<@>` で設定欄の書体へ | `<@>` は 1 つ前ではなく設定欄の書体へ戻る |
| `H<s50>H<s>H<s*2>H<s+20>H` の大きさが 100・50・100・200・220 | `+` `-` `*` はその時点の大きさに効く `<s>` は大きさと `<s>` で指定した書体を戻す |
| `<#ff0000>` は字だけ赤、`<#00ff00,0000ff>` は縁も青、`<#red>` は ff0000 | 2 つ目は影・縁色 色の名前は既定のプリセット色（`default.palette` の名前の付いた 8 色） |

比べた結果（`report.json` の見本ごとの差の平均 24 本） 読む前 8.32 → 読んだ後 0.10

| `H<s50,ＭＳ ゴシック>H<@>H` の 3 文字目が Arial の 50 | `<@>` は `<s>` で指定した書体も戻すが、大きさは残す |
| `<@Arial,1>`〜`<@Arial,6>` が影・薄い影・縁・細い縁・太い縁・角の縁 `<@,3>` は何も変えない | 番号は `aviutl2.txt` の文字装飾 書体名が空なら丸ごと効かない 縁と影は影・縁色 |
| `<@+B>` で太字、`<@-B>` で戻る、`<@+I>` で斜体、`<@>` で素の字 `<s,,B>` も同じ | スタイルは B と I を読む 取り消し線（S）は読まずに数える |
| `<s,,,0>` `4` `8` `20` で縁取り文字の H が 57・61・65・76 | 縁の太さの数は両側の合計（片側に半分） 設定欄に縁が無い字には付けない（測っていない） |
| 字間 20 の上の `<gw40>` で字の間が 40、行間 20 の上の `<gh40>` で行の間が 40 | 設定欄に足さず置き換える 字間はその字の前、行間はその行の終わりの値で次の行との間 |
| `<tw0.5>` `<th0.5>` `<tr45>` の字が送り幅を変えずに枠の真ん中で縮み、時計回りに回る | 字の枠（送り幅 x 行の高さ）の真ん中を中心に 1 文字ずつ変形する `<tr+15>` は今の角度に足す |
| `H<//コメント//>H</>H` が H 3 つ | コメントと区切りは字を出さない |

比べた結果（読まない物を除く見本 字の外形） 1〜2 画素以内 縁取り文字の縁は前からの表
（`compat/decoration.py`）が AviUtl2 より片側 2〜3 画素細かった 表は #184 で測り直した（下の
「フィルタと中身を AviUtl2 で測る」）

まだ読まない物（文字のまま残す 黙って捨てると描けていないことに気付けない 実物の配布物 326 本には
1 度も出てこなかった）

- `<r>` `<w>` `<c>` 時間で出る字が変わる（見本 `tag39`〜`tag41` 見本の長さの中で `<r5>` の後は
  1 文字だけ、`<w1>` の後と `<c>` の前は出なかった）
- `<p>` 座標 相対は字をずらした分だけ行の幅と高さを広げ、`<p>` で戻した後は広げない 絶対は
  組み方の枠まで変わる（見本 `tag34` `tag35` `tag52`）
- ふりがな `<!>`、絵文字 `<&>`、プリセット `<$>`、本人が書き換えたプリセット色
- 大きさを変えた字の縁取りの太さ（今は設定欄の大きさで決まる）

縦に伸ばしたり回したりした字は、文字の枠（テキストの入れ物）で切る（#184 AviUtl2 は `H<th2>H<th>H` の
真ん中の字を高さ 114 の枠の上下で切った）

### シーンチェンジは場面切り替えとして描く

AviUtl のシーンチェンジ（`.exa` の `[v.0]` `_name=シーンチェンジ`）は、YMM4 のために作った
場面切り替え（生成オブジェクト `transition`）として置く（#196） 前の場面と後の場面の取り方
（頭より前に始まったクリップを切れ目の手前で止めた物と、今の時刻の下の絵）も YMM4 と同じ

- スクリプトの物（`name=ディザワイプ(時計)@ディザσ`）は、`.scn` のスクリプトを場面切り替えの
  効果の列に積む 描く側は種類の拡張子（`.scn` `.scn2`）で見分け、前の場面へ掛ける効果とは
  別に走らせる（`engine/render/renderer.py` の `_draw_scene_change`）
- **前の場面をオブジェクト、後の場面をフレームバッファ**に入れて走らせ、フレームバッファ
  （後の場面）の上へスクリプトの描画を重ねる 進み具合（0〜1）は `obj.getvalue("scenechange")`
  向きは配布物 4 本の書かれ方から読んだ どれも 0 でオブジェクトをそのまま描き、1 へ向けて
  オブジェクトを削ってフレームバッファを見せる
- `調整` はスクリプトの `track0` として読む（配布物 4 本とも `track0` の行が無く、`調整` と
  `track1` だけがある） `反転` は意味を確かめていないので数える
- 走らないスクリプトは真ん中で入れ替えるだけにして（素通し）、
  「シーンチェンジのスクリプトが走らない（素通し）: 名前」と数える
  **ffi は許さない**（2026-09-25 利用者の決定 配布スクリプトから任意のメモリや DLL に
  触れられるため） 実物の sigma のディザ 4 本はどれも `sigma_dither` を通して ffi を使うので、
  ここへ来る（ディザフェードアウトイン は ffi を使わない真ん中の 1 枚と頭の 1 枚だけ走る）
- 組み込みは名前で写せる物だけ（`クロスフェード` → `fade`） 名前の無い物は `type` の番号で
  数える 番号と種類の対応、AviUtl2 の書き方は実物が無く確かめていない

どれも実物の AviUtl で並べて測ってはいない 測るときは、前後の場面の取り方・進み具合の
数え方（こちらは範囲の頭から `経過 / 長さ` 最後のフレームでも 1 にならない）・
場面に黒を敷くことを見る

## 6. Git の使い方

### ブランチ

| | |
|---|---|
| `main` | 常に `tools/verify.py` が通る状態を保つ |
| `phase/*` | フェーズ単位の作業 例 `phase/p7-proxy` |
| `fix/*` | 不具合の修正 |

`main` へ直接 push しない

### PR はフェーズ単位

1 フェーズ = 1 PR 細かく切りすぎると全体像が見えず、大きすぎるとレビューが
成立しない **フェーズの完了条件を満たしたら PR を出す**

PR には必ず含める:

- 何をしたか、**なぜその作りにしたか**
- `tools/verify.py` の結果（テスト件数）
- 途中で見つけた不具合と、その直し方
- 実物で確かめた場合はその結果（「配布物 36 本すべて通した」など）

### 懸念点は同じブランチで直す

作業中やレビューで出た懸念点は、別の Issue や PR に分けず、**できるだけ今のブランチで直す**
（利用者の決定） PR を分けるとレビューの回数が増え、同じ所を何度も見直すことになる
切り出すのは、今のブランチで直せない物だけ

- 実物のアプリ（AviUtl・YMM4・配る本体）の起動や、利用者の判断が要る物
- 外のライブラリの中（こちらのファイルからは包めない物）

切り出したときは、直せなかった理由を Issue に書き、PR の本文からも示す
レビューの道具（`.coderabbit.yaml`・`AGENTS.md` の「Review guidelines」）にも、別の PR に分けるよう
勧めず、この PR の中で直す前提で指摘するよう頼んである

### AI のレビューを受ける

レビュー役は 4 つ どれも無料枠（Copilot は Pro の月の回数）で動かしているので、
回数が切れる役が必ず出る **PR を出したら Codex 以外の全員に頼み、指摘を突き合わせる** 枠が
切れた役は飛ばしてよい Codex は使う量を抑えるため、最後に 1 回だけ頼む
（下の「Codex のレビューは最後に 1 回」）

| レビュー役 | 頼み方 | 設定 |
|---|---|---|
| [CodeRabbit](https://coderabbit.ai/) | PR で `@coderabbitai review`（公開リポジトリでは自動で走らない） | `.coderabbit.yaml` |
| GitHub Copilot | `gh pr edit <番号> --add-reviewer @copilot`（自動にはしない 月の回数を守るため） | なし |
| Sourcery | `@sourcery-ai review` | Web の画面（Review Settings） 言語は日本語、`tests/fixtures/**` を外す |
| Codex | `@codex review`（CodeRabbit の承認の後に 1 回） | `AGENTS.md` の「Review guidelines」 |

#### 承認（Approved）の出し方

CodeRabbit と Sourcery は承認を出す 指摘が残っている間は「変更を求める」状態で、
全部片付くと承認に変わるので、**PR の一覧を見るだけで手が要るかどうかが分かる**

- CodeRabbit … `.coderabbit.yaml` の `reviews.request_changes_workflow: true`
  承認へ変わるのは「指摘が全部解決」「最新のコミットまで見た」とき
  **こちらの CI の結果は見ていない** CI が赤でも承認は出るので、承認を CI の代わりにしない
- Sourcery … Web の画面（Review Settings）の `Let Sourcery approve pull requests`
- Copilot の承認は**有効にしない** 既定のまま（指摘だけ） 承認 1 つで必須承認を
  満たせてしまい、門として弱くなるため
- Codex は指摘のコメントを書くだけで、承認を門には使わない

**承認はマージの門ではない**（`main` の必須承認は 0 のまま）
門は CI 2 本（`verify (3.12)`・`verify (3.14)`）と会話の解決

ただし **CodeRabbit の「変更を求める」は、必須承認が 0 でもマージを止める**
（PR #18 で確かめた `reviewDecision` が `CHANGES_REQUESTED` になり `BLOCKED` に変わる）
止まったときの外し方は 2 つ

1. 指摘を直すか返事をしてスレッドを解決し、`@coderabbitai review` で見直してもらう
   （これが普通の道 承認へ変わる 見るのは前回のレビューからの差分なので、
   PR 全体を見直してほしいときは `@coderabbitai full review`）
2. CodeRabbit の枠が切れて見直しが返ってこないときは、**管理者が GitHub の画面で
   その レビューを Dismiss する**（`main` の保護は管理者に強制していないので外せる）

`@coderabbitai approve` と `@coderabbitai resolve` は**使わない** 指摘を見ないまま
承認や解決ができてしまい、承認の表示と実際に見た範囲が食い違う

約束（コメントの書き方・コア層の依存・テストの書き方）は、どの役にも同じものを渡す
`.coderabbit.yaml` を直したら、`AGENTS.md` の「Review guidelines」もそろえる

#### Codex のレビューは最後に 1 回

Codex（ChatGPT の `chatgpt-codex-connector`）は PR に `@codex review` と書くと見る
指示は `AGENTS.md` の「Review guidelines」の節から読む（日本語で書く・重さ P0〜P2 を付ける・
重い問題を中心に見る・書き方や言い回しは CodeRabbit に任せる） Codex は `AGENTS.md` を
32KiB までしか読まないので、この節は短く保つ

使う量を抑えるため、頼む回数を決めてある

1. CodeRabbit の指摘を直し、承認を取る
2. 最後に `@codex review` を 1 回だけ頼む
3. Codex の P0・P1 を直したときだけ、もう一度 `@codex review` で頼み直す
4. P2 は直してスレッドに返信し、締める（頼み直さない）

Codex はマージの必須条件にしていない（`main` の必須の検査は `verify (3.12)` と
`verify (3.14)` だけ） 頼み忘れても止まらないので、マージの前に Codex の
レビューが済み、P0・P1 が残っていないかを自分で見る

以前は Qodo を使い、`Qodo review` という status を必須にしていたが、試用が切れて
レビューが止まったのでやめた（status を出す workflow と判定の道具も消した）

Gemini Code Assist（GitHub の PR レビュー）は使わない GitHub 向けの無料 consumer version は
2026-07-17 に提供を終え、GitHub のレビュー機能で残っているのは Google Cloud の有料契約が要る
enterprise 版だけのため

- **指摘は読んで判断する** 機械的に全部直すのでも、全部無視するのでもない
- 直さないときは、その理由を PR のコメントに残す
- **同じ指摘が何役からも来る** 直すのは 1 回で、どのスレッドにも同じコミットを示して返す
- 役どうしで言うことが食い違ったら、どちらを採ったかと理由を PR に残す

#### Dependabot の PR

CodeRabbit は契約の席を人にしか割り当てないので、Dependabot などボットが作った PR は
「Review skipped」と書くだけで審査しない
（[席の割り当て](https://docs.coderabbit.ai/management/seat-assignment)）
Codex は枠が小さく、毎月届く更新すべてには使えない そこで扱いを次のように決めた

- `.github/dependabot.yml` の `groups` で、種類（`package-ecosystem` GitHub Actions・pip）ごとに
  1 本の PR へまとめる 1 部品 1 本だと、同じ確かめ方を何度も繰り返すことになる
- 大きな版上げ（major）と小さい物（minor・patch）は別の PR に分ける 確かめる手間が違い、
  混ぜると小さい物まで大きな版上げの確かめ方に巻き込まれる 分けても 1 つの種類で月に多くて 2 本
- pip は版上げの PR を出させず（`open-pull-requests-limit: 0`）、脆弱性の修正だけが届く
  そのまとめ方は `applies-to: security-updates` で指す
- `.coderabbit.yaml` の `reviews.auto_review.ignore_usernames` に `dependabot[bot]` を入れ、
  「Review skipped」の書き込みも出させない

マージの前に確かめること

1. CI がすべて通る（必須の `verify (3.12)`・`verify (3.14)` だけでなく、PR に付いた検査すべて）
2. 変わったのが版の数字（とロックファイル）だけ ほかの行が変わっていたら、なぜかを読む
3. 大きな版上げなら、部品の変更点（リリースノート・CHANGELOG）を読み、こちらの使い方
   （workflow の `with:` の入力・呼んでいる関数・動く環境の下限）が変わる所が無いか見る

大きな版上げのときだけ `@codex review` を 1 回頼む 小さい物は上の 1・2 で足りるので頼まない
P0・P1 が出たときの扱いは人の PR と同じ（上の「Codex のレビューは最後に 1 回」）

### コミットメッセージ

1 行目に何をしたか、空行を挟んで**なぜそうしたか** 日本語で書く

```
YMM4 互換を、実配布の .ymmt に合わせて書き直す

1 バイト目で落ちていた

実物と違っていたのは 4 点
- .ymmt は ZIP 中の catalog.json が本体
...
```

## 7. リリース

正式リリースの条件と残っている課題は
[Issues](https://github.com/kagemorikosame/sashimono-edit/issues) と
[マイルストーン](https://github.com/kagemorikosame/sashimono-edit/milestones)で追う

いまは **β 版** 作りが大きく変わることがある 互換の穴（AviUtl / YMM4 で
まだ再現できていないもの）は、実際に呼ばれた回数つきで Issue に出す
数の多い順に埋める方針なので、回数が書かれていないと優先順位が付けられない

### 配る zip を作る

```
.venv\Scripts\python.exe tools\build_package.py
```

`dist\SashimonoEdit-<版>-windows-x64.zip` ができる 最後に**その zip を別の場所へ展開し、
中の exe で `--self-check` を走らせる**ところまでが 1 回の作業

- 組み立てた直後のフォルダで確かめない 開発機の Python や DLL を拾って通ってしまう
  配るのは zip なので、zip から確かめる 確かめるときの `PATH` も Windows の分だけにする
- `--self-check` は画面を出さずに、GL で描く・書き出す・Lua を走らせる・pip が
  あるか、を 1 行ずつ出す 起動しただけでは積み忘れは分からない
  （読み込みは遅延で、呼んだ時点で初めて DLL を探しに行く）
- 使う人の機械で動かないと言われたら、zip の中の `README.txt` にあるとおり
  `Sashimono.exe --self-check | more` の結果を貼ってもらう
- 字幕起こしと AI 連携は積まない（合わせて 2 GB を超える） 開発機に入っていても
  拾わないよう、`tools/build_package.py` の `EXCLUDED_MODULES` で外している
- **名前で読み込む部品**（lupa の Lua の実体、pip）は PyInstaller が辿れない
  組み立ては通ってしまうので、`COLLECTED_PACKAGES` でまとめて積む
  足すときは `--self-check` にその部品を実際に動かす項目も足す
- **標準ライブラリは丸ごと積む**（`stdlib_arguments` Tk・Python 自身の試験・開発の道具は
  除く） 後から入れる部品（AI 連携・字幕起こし）とその依存が使う標準ライブラリは、
  本体が import しないと積まれない AI 連携を入れて送った途端に `No module named
  'zoneinfo'`（pydantic が読む）で止まった 1 つずつ足すと次の穴で落ちるので丸ごと
  2026-10-01 に測った増え方は、展開して 229 → 231 MB、zip で 95 → 96 MB tzdata は積まない
  （zoneinfo を import するだけでは要らず、時刻の名前を引く所が無い）
- 本体も一部を使うので配布版に入り、後から入れる部品も使う包み（cryptography など
  `SHARED_WITH_ADD_ONS`）は下の部品まで全部積む 配布版に入った包みは、後から入れた置き場の
  同じ包みより先に読まれ、本体の使う部品だけでは mcp の読む物が無かった
- 後から入れた置き場の `.pth` も読む（`runtime.read_path_files`） pywin32 が要る
- 組み立てた後に、後から入れる部品が import する標準ライブラリが配布版に全部あるかを字面で
  数える（`missing_stdlib`） zip からの確かめでは、この機械に部品が入っていれば、配布版の
  exe の中で import してみる（`--import-check` 入れた置き場と同じく前へ足して読む）
  試験のためには落とさない（手元の .venv にある物で確かめる）

依存が何も入っていない機械（VC++ ランタイムなど Windows 側の部品も無い）での
確認は、開発機ではできない **CI のまっさらな Windows で zip だけを持って確かめる**（Issue #33）

### まっさらな Windows で zip から起動する（CI）

`.github/workflows/package.yml` が zip を組み立て（build）、別の機械（clean-machine）へ zip だけを
渡して `tools/check_clean_machine.ps1` を走らせる 確かめる機械には Python・uv・依存を入れない

- 展開先と使う人の置き場（APPDATA・LOCALAPPDATA・USERPROFILE・TEMP）は `C:\テスト 利用者\…`
  （日本語と空白） 環境変数は Windows の分と置き場だけにして、PATH から runner の Python・
  uv・FFmpeg を外し、PYTHONHOME や PYTHONPATH も渡さない
- **ファイアウォールと監査の設定に触るのは CI の runner（`GITHUB_ACTIONS` が true）だけ**
  触る前の設定（各プロファイルの有効・無効と監査の設定）を控え、終わりに（落ちても）戻し、
  足した規則も消す 送り出しの既定には触らない 手元で走らせると、この確かめは理由を出して飛ばす
- `-Root` に前からあるフォルダを渡すと止まる 消すのは、この道具が作った印（`.sashimono-clean-check`）
  のあるフォルダだけ
- exe はファイアウォールで外へ出られなくする（CI） 自己診断（自動更新の項目を含む）は外へ出ずに
  通らなければならない 止めた接続は Windows Filtering Platform の監査（イベント 5157）で exe ごとに
  数え、自己診断の間に 1 件でもあれば落とす（ファイアウォールの記録 pfirewall.log は runner では
  何も書かなかった） 先に別の exe（curl の写し）で、止まることと数えられることを確かめる
- 環境変数は削りすぎない 素の Windows の利用者が持つ変数（ProgramFiles・PATHEXT・PSModulePath
  など）は渡す 外すと PowerShell 5.1 の起動が遅くなり、使う人の機械では起きない失敗になる
  その利用者が初めて PowerShell を起こすときは、CI で 11〜22 秒かかった 入れ替え係が走り始める
  のを待つ時間（`swap.START_SECONDS`）はこれを見て 60 秒にしてある
- 自己診断の結果を 1 項目ずつ実行の要約へ書く **GPU が無いので GL の 2 項目（描く・書き出す）
  だけは、GL の理由（`GLContextError`）で落ちていれば通す** ほかの項目は全部通らなければ落とす
  FFmpeg は GL を通さない項目（日本語のフォルダへ符号化して読み戻す）で確かめる
- exe の pip で見本の wheel を日本語のフォルダへ入れる
- 引数無しで起動して窓が出ること、GL の無い機械で描けない理由をプレビューの所に出したまま
  動き続けること、閉じて終了コード 0 で終わること（#149）を見る 窓の写真とログは
  `clean-machine-report` として残る
- 実の利用者の置き場（runner の `%APPDATA%\Sashimono` など）に書いていないことを見る

タグのとき（`release.yml` から呼ばれたとき）と手動のときだけ、組み立ての前に ffmpeg を入れて
`tools/verify.py` も走らせる タグの push では ci.yml が走らないため main と PR では ci.yml が
走らせるので二重にしない 本番のタグで初めて走らせて落ちると公開が止まるので、出す前に
`gh workflow run package.yml --ref <ブランチ>` で同じ道を通しておける
ffmpeg の版とハッシュは `.github/actions/ffmpeg` の 1 か所（ci.yml と package.yml が使う）
走らせるのは main への push、タグの push（`release.yml` から呼ぶ 落ちたら下書きへ上げない）、
手で（workflow_dispatch）、組み立てと確かめに関わるファイルを変える PR 組み立てだけで
10 分ほどかかるので、ほかの PR では走らせない

CI で組むときは、積む包みを `THIRD_PARTY_NOTICES.md` の一覧の版に留める
（標準ライブラリだけで動く `tools/package_notices.py --write-constraints` で、依存を入れる前に
制約を書き、最初の `uv pip install -c` から使う 制約の無い導入を先に通すと、その日の新しい
依存が壊れていたときに制約まで届かずに止まる） 依存では入らないが積む包み（pip Python に最初から
入っている）は制約では入れ直されないので、`--write-requirements` で一覧の版の要件を書き、
同じ導入で `-r` で入れる（`package_notices.INSTALLED_BESIDE` 必ず積む包みを足したら、依存か
ここのどちらかに入っていることを試験が見る）
依存は下限だけで書いてあるので、留めないとその日の最新が入り、一覧と版が食い違って止まる
（2026-10 に av 19 が出て、写しの無い DLL を積もうとして止まった） 包みを上げるときは、
一覧と写しを先に直す

CI には GPU が無いので、**GL で描く確かめは開発機の `build_package.py`（zip からの確かめ）**で行う
Qt のソフトウェアの GL（`opengl32sw.dll` Mesa llvmpipe）は積まない 取れるのは OpenGL 3.0 までで、
描く関数は PyOpenGL が Windows の `opengl32.dll` から引くので Qt がそちらで作った
コンテキストへ届かず、積んでも GPU の無い機械では描けない（`UNUSED_QT_PARTS`）

### 使用許諾（配る zip は GPL の条件で配る）

Sashimono 本体のソースは MIT PyAV の wheel に入っている FFmpeg は組み込みの表記が
「LGPL version 3 or later」だが、同じ wheel に GPL の libx264 と libx265 が入っていて、
CPU での書き出しは libx264 を使う **zip は全体として GPL の条件で配る** と決めた
（Issue #32） 本体の MIT は GPL と両立するので、ソースは MIT のまま

- 部品ごとの使用許諾とソースの入手先は `THIRD_PARTY_NOTICES.md` に手で書く
  zip には `THIRD_PARTY_NOTICES.txt` として入る
- GNU の使用許諾の全文は `licenses/` に置く（どの包みも dist-info に持っていないため）
- PyAV の wheel の DLL（FFmpeg・x264・x265 ほか）と LuaJIT も写しを持っていないので、
  上流から積んだのと同じ版の写しを取ってきて `licenses/<部品>-<版>/` に置いてある
  版と取得元は `THIRD_PARTY_NOTICES.md` の表に書く PyAV を上げたら、pyav-ffmpeg の
  組み立て設定（`scripts/pkg.py`）で版を確かめて取り直す
- Python の包みの使用許諾は、組み立てのたびに dist-info から `licenses\<名前>-<版>\` へ写す
  **包みの名前は決め打ちにしない** 組み立ての記録（PyInstaller の TOC）から、積んだ
  ファイル 1 つずつの出どころを辿って数える PyInstaller は入っていれば拾うので、組み立てる
  機械が変わると積む包みも変わる
- 次のどれかがあると、zip を作る前に止まる
  - 出どころの分からないファイル（どの包みでも、Sashimono のソースでも、Python 本体でもない）
  - 使用許諾の写しが見つからない包み（写しを持たない包みは `WITHOUT_LICENSE_FILES` で名指しする
    その前に `THIRD_PARTY_NOTICES.md` へ書く）
  - `THIRD_PARTY_NOTICES.md` の一覧に無い包み
- 使わない Qt の部品（PDF を絵として読むプラグインと Qt6Pdf、仮想キーボードと
  それが読む Qt6Quick・Qt6Qml）は組み立てたあとに外す（`UNUSED_QT_PARTS`） 外した物を
  残った DLL が読んでいないかは、組み立てのたびに DLL の import 表で確かめる
  外すと zip が 8 MB 小さくなり、qtwebengine（580 MB）などのソースを添付しなくてよくなる
- wheel の中の DLL（`av.libs`）と LuaJIT は、`NATIVE_LICENSES` でリポジトリの写しと
  結び付ける 表に無い DLL が増えたら止まる
- 包みの版は一覧の表の版と突き合わせる 依存は下限だけで指定しているので、新しい版が
  入ったら一覧を直すまで zip を作らない
- `--skip-build` でも、組み立ての記録に無いファイル（手で足した DLL など）がフォルダに
  あれば止まる
- zip から確かめる段では、使用許諾の一覧と写しが組み立てたときと同じ中身か（sha256）を見る
- 組み立てる間は `PATH` を Windows の分にする 開発機の `PATH` にある
  Git for Windows の OpenSSL が、Qt の通信部品のためとして積まれていた
- zip から確かめる段でも、一覧と全文が入っているかを見る
- Qt は LGPL-3.0 で使う onedir で組み立てるので Qt の DLL は別のファイルのまま残り、
  使う人が差し替えられる 1 つの exe へまとめる形（onefile）に変えるときは、これを考え直す

### リリースにソースを添付する

GPL と LGPL の部品（FFmpeg・x264・x265・LAME・libiconv・Qt・PySide6）は、配る側が
対応するソースを渡せる状態を保たなければならない 上流の置き場は消えたり移ったりするので、
**zip と同じ GitHub Release に、積んだのと同じ版のソースを添付する**

リリースでは `tools/release.py`（下の「自動更新のリリース」）が、下書きから落とした zip を
展開した物を数えてここを走らせ、下書きへ上げる 飛ばすのは、下書きの `sources-manifest.json` に
載ったファイルが全部、同じ大きさと sha256 で下書きにあり、`sources-SHA256SUMS.txt` もあるときだけ
欠けていれば足りない分だけ上げ直す 上げるときは本体を上げ終えてから、別の呼び出しで索引
（`sources-manifest.json` と `sources-SHA256SUMS.txt`）を上げる 1 回で並べて上げると、途中で落ちた
ときに索引だけが上がり、次に打ったときに揃ったと見て、ソースが欠けたまま公開まで進む
手で行うときも、本体 → 索引の順に上げる

```
.venv\Scripts\python.exe tools\collect_sources.py --check
.venv\Scripts\python.exe tools\collect_sources.py
gh release upload <タグ> dist\sources\*.tar.* --clobber
gh release upload <タグ> dist\sources\sources-SHA256SUMS.txt dist\sources\sources-manifest.json --clobber
```

- `--check` は入手先に届くかだけを見る（中身は落とさない） 落とすと 100 MB ほど
- Qt のソースは、組み立てたフォルダ（`dist\Sashimono`）に積んだ Qt のファイルが属する
  モジュールの分だけ落とす（`QT_FILE_MODULES`） 先に `tools/build_package.py` を走らせる
  どのモジュールの物か分からない Qt のファイルがあれば止まる
- 落とすと `dist\sources` にアーカイブと `sources-SHA256SUMS.txt` `sources-manifest.json`
  （取得元・版・sha256）ができる 上流が sha256 を公開している物は照合し、合わなければ止まる
- 版は `tools/collect_sources.py` に手で書いてある 入っている PyAV（の FFmpeg）と PySide6 の
  版と食い違うと落とす前に止まる 上げたら一覧と `THIRD_PARTY_NOTICES.md` を一緒に直す
- x264 の本家（code.videolan.org）は道具からの取得をボット避けの画面で断るので、同じ
  コミットを持つ GitHub の写しから落とす

### 報告の受け口

使う人の不具合の報告・要望・質問は **Discussions** で受ける **Issue は開発者が直す作業の置き場**
Discussions で確かめた報告（再現した不具合、取り掛かると決めた要望）を、開発者が Issue に起こし、
元の Discussion へのリンクを書く 確かめる前の報告と質問が Issue の一覧に混ざると、
直す作業の数と優先順位が読めなくなる

- ソフトの〔ヘルプ〕→〔不具合・要望を送る〕とバージョン情報、配る zip の `README.txt` は
  `sashimono.links.REPORT_URL`（Discussions のカテゴリを選ぶ画面）を指す
- Issue の雛形は置かず、白紙の Issue も閉じてある（`.github/ISSUE_TEMPLATE/config.yml`）
  Issue を作る画面は Discussions の各カテゴリへの案内だけを出す 書き込み権限のある人は白紙で作れる
- カテゴリの書き込み欄は `.github/DISCUSSION_TEMPLATE/<スラッグ>.yml` 受け付けるのは
  `body` `labels` `title` だけ（Issue の雛形の `name` `description` は書かない）

| カテゴリの名前 | スラッグ | 説明に書く言葉 | 書き込み欄 | 形式 |
|---|---|---|---|---|
| Bug reports | `bug-reports` | 不具合の報告 動かない・落ちる・思った通りにならない | `bug-reports.yml` | Open-ended discussion |
| Compatibility | `compatibility` | 互換（AviUtl／YMM4）の報告 配布物が読めない・違って見える | `compatibility.yml` | Open-ended discussion |
| Ideas | `ideas` | 要望 こういうことができるようにしてほしい | `ideas.yml` | 最初からある物 |
| Q&A | `q-a` | 質問 使い方・どちらか分からないこと | `q-a.yml` | 最初からある物（Question / Answer） |

名前を英語にしているのはスラッグを決めるため 日本語の名前から GitHub がどんなスラッグを
作るかは確かめていない 日本語は説明と書き込み欄の中に書く

**スラッグはカテゴリの名前から GitHub が作り、名前を変えるとスラッグも変わる** 書き込み欄の
ファイルの名前がスラッグと違うと、GitHub は欄を出さずに白紙の書き込みにする スラッグは
カテゴリを開いたときの URL（`/discussions/categories/<スラッグ>`）で確かめる 変えたら
書き込み欄のファイルの名前、`config.yml` の行き先、`sashimono.links.DISCUSSION_CATEGORIES` を
一緒に直す（`tests/test_help_links.py` が食い違いを落とす）

### 色の範囲

扱うのは **SDR の sRGB / Rec.709 だけ** HDR と広色域は今後の課題（Issue #32 で決めた）
新しく色を扱う処理を足すときも、この範囲を前提にしてよい 範囲の外の素材を正しく
扱うふりはしない

色の変換と印は `src/sashimono/engine/colorspace.py` の 1 か所にまとめてある
YUV と RGB の行き来は全部 PyAV（swscale）に任せ、自前の行列やシェーダーは持たない
（2026-10-02 に実装と突き合わせた 変えたらこの表も直す）

| 所 | いまの動き |
|---|---|
| 書き出し | `yuv420p`（8 ビット）へ **BT.709 の行列・リミテッドレンジ**（16〜235）で変換し、ストリームに `color_primaries=bt709` `color_trc=bt709` `colorspace=bt709` `color_range=tv` を書く（`to_bt709` `tag_bt709`） 変換の行列と印は必ず同じ |
| 書き出しの符号化方式 | 画面で選べるのは `h264_nvenc` `h264_qsv` `libx264` 印はどれにも同じく付く |
| 色の印を外から変える | `color_*` の指定と、`x264-params` などの中の `colorprim` `transfer` `colormatrix` `range` は書き出す前に断る 行列と印が食い違うのを防ぐため |
| 伝達特性の印 | 合成した値は sRGB の曲線だが、印は `bt709` にする 再生ソフトと動画サイトが sRGB の印（`iec61966-2-1`）を扱えないことがあるため（意図した食い違い `colorspace.py` に理由） |
| 読み込み（映像） | 素材の行列の印と範囲の印（`colorspace` `color_range`）に従って RGBA へ変換する 印の無い素材は大きさで見当を付ける（幅 1280 以上か高さ 576 超えは BT.709、それ以外は BT.601） フルレンジ（`yuvj*` など）も印どおりに読む |
| 読み込み（静止画・エフェクトの画像） | 同じく PyAV で RGBA にする ICC プロファイルと PNG の gAMA・cHRM は**読まない**（sRGB とみなす） |
| 控え（プロキシ） | 書き出しと同じく BT.709・リミテッドレンジに変換して印を付ける |
| 合成 | 素材は sRGB のテクスチャ（読むと線形）で受け、半精度の画面で合成し、最後に sRGB の曲線へ戻す 半透明の混ぜ方はプロジェクトの設定（「半透明の重ね合わせはプロジェクトの設定」） エフェクトはいつも線形で計算する |
| プロジェクトの `color_space` | `rec709` を保存するだけで、描画も書き出しも読まない（将来 HDR を足すときの置き場） |

範囲の外の素材（いまの動き 直すときはここを消す）

- **HDR（PQ / HLG）と BT.2020** 変換はしないが、見分けて知らせる 行列だけ BT.2020 で変換し、
  伝達特性と原色は変換せずに SDR として出すので、白っぽく褪せて見える トーンマッピングは無い
  控えには、中身は PQ / HLG のままなのに `bt709` の印が付く（原本の見え方とは揃っている）
  - 見分けは素材の印だけで行う 読み込みの調べ（`probe.py`）が伝達特性（`color_trc`）と原色
    （`color_primaries`）を `VideoStreamInfo.color_transfer` `color_primaries` に覚え、保存もする
    `smpte2084`（PQ）と `arib-std-b67`（HLG）は HDR、原色の `bt2020` は広色域と呼ぶ
    （`VideoStreamInfo.color_outside_sdr`） 印の無い素材は推し量らない
  - 読み込んだときに 1 度だけ窓で知らせる（`ui/hdr_notice.py` まとめて読み込んだ分は 1 つの窓
    同じファイルはその窓を閉じるまで 2 度出さない） 設定の「HDR の素材を読み込んだら知らせる」
    （`Preferences.hdr_notice` 既定は入）と、窓の〔次から知らせない〕で切れる
  - 素材一覧の行には設定に関係なく印（`HDR（PQ）` など）を付け、補足に白っぽく出る訳を書く
  - 印を覚える前に保存した作品の素材は、印が無いものとして開く（描き方は同じで、知らせが出ないだけ）
- **10 ビット以上** 読むときに 8 ビットへ落とす 書き出しも 8 ビット（`yuv420p`）だけ
- **広色域の静止画**（Display P3 の写真など） ICC を読まないので sRGB として出る

### 自動更新の仕組み

配った zip（`Sashimono.exe`）は、自分で新しい版へ入れ替わる（Issue #36 設計は計画書の F-12）
部品は `src/sashimono/update/`（Qt を読まない）と、画面の側の `ui/updates.py`

| 段 | すること | 場所 |
|---|---|---|
| 確かめる | 起動して 3 秒後に裏で、目録（`update.json`）と署名（`update.json.sig`）を固定の URL から読む REST API は叩かない 数時間に 1 回まで 失敗は黙る | `update/check.py` |
| 信じる | 埋め込んだ公開鍵（2 本）のどちらかで署名が通ったときだけ中身を読む **公開鍵が入っていない版は何もしない** | `update/signing.py` |
| 落とす | 転送を追う 行き先は `github.com` と GitHub の CDN だけ（下の注） 大きさと SHA-256 を目録と照らす | `update/fetch.py` |
| 置く | 今の版のフォルダの隣（`Sashimono.new`）へ展開し、中の `build-info.json` の版と Python の ABI を目録と照らす | `update/package.py` |
| 入れる | 本人の合図（〔今すぐ再起動して入れる〕か〔次の起動で入れる〕）で、本体の外の PowerShell が改名で入れ替える | `update/swap.py` |
| 戻す | 入れた版が 2 回続けて窓を出せなければ前の版へ戻す メニュー〔ヘルプ〕→〔前の版に戻す…〕でも戻せる | `update/swap.py` |

- 固定の URL は `links.py` の `STABLE_MANIFEST_URL`（`releases/latest/download/update.json`）と
  `BETA_MANIFEST_URL`（`releases/download/beta/update.json`） **配った版が読み続けるので変えない**
- 転送先は計画書では `objects.githubusercontent.com` だったが、2025 年から GitHub は
  `release-assets.githubusercontent.com` へ転送している（2026-10-02 に実物の転送先を見て確かめた）
  両方を許す（`fetch.py` の `ALLOWED_HOSTS`）
- 目録の形（`schema` `version` `minimum` `python_abi` `notes_url` `package{url size sha256}`）は契約
  キーを消したり意味を変えたりしない 足すのは自由（古い版は知らないキーを読み飛ばす）
  形を大きく変えるときは `minimum` を上げ、古い版には配布のページを案内させる
- 入れ替えは同じ親の下の改名だけ（`Sashimono` → `Sashimono.previous`、`Sashimono.new` → `Sashimono`）
  親に書けない場所（`Program Files`）では入れ替えず、配布のページを案内する 既定の置き場は
  `%LOCALAPPDATA%\Programs\Sashimono`（zip の README に書いてある）
- 入れ替え係は Windows に入っている PowerShell 5.1 に、`swap.py` の台本を毎回書いて渡す 別の
  実行ファイルを作らないのは、Python を積んだ物をもう 1 つ配り、それ自身も入れ替える羽目になるため
  場所は環境変数で渡す（日本語の名前でも化けない） 走り始めた印を見てから本体を終える
  （台本の実行を止めた会社の機械で、本体だけ消えて誰も起こし直さない、を防ぐ）
- 新しい版は窓を出したところで印のファイルを書く（`app.py` の `mark_started`） 書かずに落ちたら
  入れ替え係が数え、2 回続けば `Sashimono.failed` へよけて前の版を起こす 戻した版は次から飛ばす
- 編集・書き出し・AI の作業・字幕起こしの途中では再起動しない（`MainWindow.update_blockers`）
  保存していない変更は、入れ替え係を起こす**前に**尋ねる 取り消されたら起こさない
  （先に起こすと、迷っている間に入れ替え係が待つのを諦めて今の版を起こし、本体が 2 つ動く）
- Release の workflow は組み立て（依存を入れる 書く権限なし `persist-credentials: false`）と
  下書きへ上げる（依存を入れない `contents: write`）をジョブで分ける 依存のどれかが悪さをしても、
  リリースを書き換えられるトークンに届かない
- 本人の持ち物（設定・スクリプト・テンプレート・入れた実行環境）はフォルダの外にあるので消えない
  （下の「更新で消えない置き場」） exe の隣の `scripts` に置かれた物は、入れ替える前に新しい版へ写す
  （`carry_user_files`） 前の版へ戻すときも、戻る先の版へ写す（戻すと今の版は `.previous` へ回り、
  次に新しい版を入れたときに消える）
- Python が上がる版（`python_abi` が変わる）では、入れてある字幕起こしと AI 連携の環境が読めなくなる
  入れる前の確認でそう言い、入れた後は導入先を読まずに「入れ直してください」と出す
  （`runtime.stale_runtime` 導入先の `.python-abi` に機能ごとの ABI を書いておく） 消しはしない
  確認には、入れ直しが要る機能と、落とし直す大きさと時間の目安を添える（`update/reinstall.py`）
  大きさは今の導入先を実際に測る（入れ直すと同じ物をもう 1 度落とす） 1.5 秒で測り終えなければ
  機能ごとの目安（`FeaturePack.size_mb`）を使い、目安だと書く 時間は 100 Mbps と 20 Mbps の 2 つで出す
  配布のページから手で入れ替えるよう案内するとき（自動では入れ替えられない置き場・`minimum` より
  古い版）も、手で確かめた窓に同じ案内と exe の隣の `scripts` の注意を添える
- 古い形式のプロジェクトを今の形式で上書きする前に、横へ `名前.sme.bak` を残す
  （前の版へ戻した人が、上げる前の作品を開けるように）
- 好みは `Preferences` の `update_check`（起動時に確かめる 既定は入）・`update_beta`
  （ベータも受け取る 既定は切）・`update_confirm`（入れる前に尋ねる 既定は入 切ると次の起動の頭で入れる）
  確かめるのを切れば今の版に留まる（〔ヘルプ〕→〔更新を確かめる…〕で手で確かめられる）
  exe の隣の `scripts` の扱いは `scripts_move`（自動で移す 既定・尋ねる・何もしない 下の「exe の隣の
  `scripts`」）

設定を切り替えたときの、待っている版（落として展開した版）と次の起動の予約は、次の表で
決める 画面で切り替えたとき（`UpdateController.apply_preferences`）も、起動の頭
（`apply_on_start`）も同じ `update.flow.reconcile` を通すので、どの向きに切り替えても
「今の好みで初めから決めた形」にそろう 予約には 2 種類ある 本人が〔次の起動で入れる〕を
選んだ物（`apply_chosen`）と、尋ねない設定が自動で付けた物

| 設定 | 向き | 待っている版 | 本人が選んだ予約 | 自動の予約 |
|---|---|---|---|---|
| 起動したときに確かめる | 入 → 切 | 残す（手で入れられる） | 外す | 外す |
| 起動したときに確かめる | 切 → 入 | 残す | （外れたまま 選び直す） | 尋ねない設定なら付ける |
| 入れる前に尋ねる | 入 → 切 | 残す | 残す | 付ける（次の起動の頭で入れる） |
| 入れる前に尋ねる | 切 → 入 | 残す | 残す | 外す |
| ベータ版も受け取る | 入 → 切 | 先行版なら外す（ボタンも下げ、置き場も片付ける） 正式版なら残す | 先行版なら外す | 先行版なら外す |
| ベータ版も受け取る | 切 → 入 | 変えない（次の確認でベータを読む） | 変えない | 変えない |

- 先にベータの決まり、次に確かめるかの決まり、最後に尋ねるかの決まりの順に当てる
  （ベータを切った人に先行版を入れない 確かめるのを切った人には何も予約しない）
- 入れ替えに失敗した版（結果のファイルに失敗が書かれた・入れ替え係を起こせなかった）は、
  尋ねない設定でも自動では予約し直さない（`auto_blocked` 起動のたびに失敗し続けて待たされない）
  本人が〔新しい版を入れる…〕から選べば入れる
- 窓を何枚開いていても、更新は 1 つずつ進める 落として展開する間は `update\stage.lock`
  （窓が持つ）、入れ替え係が走る間は `update\swap.lock`（PowerShell が誰にも開かせずに持つ）
  ほかの窓が進めている間は、落とさず・入れ替え係を起こさず、「この窓を閉じれば入れ替わる」と知らせる
  入れ替え係が走っている間に起動したら、画面を出さずに終わる（入れ替え係が新しい版を起こす）
  入れ替え係の台本と結果は起こすたびに別の名前にし、走っている間は結果を読まない
- 改名が断られて元の名前へも戻せないときは、前の版を `.previous`（戻すときは `.rolling`）から
  直に起こし、次の起動でフォルダの名前を戻すよう案内する 空の場所を起こして何も出ないままにしない
- 別の Python 向けに残った機能は、名前の上で入っていても動かせない扱いにする（`PackStatus.ready`）
  片方だけを入れ直すと導入先は読まれるので、もう片方を古い拡張モジュールのまま動かさないため
- 配る zip の確かめ（`tools/build_package.py`）は、配布版の exe の中で、使い捨ての鍵と見本の
  リリースを使って署名・照合・展開・PowerShell の入れ替えまでを通す（自己診断の「自動更新」）
  ネットワークへは出ない 試験も同じで、取り口は偽物（`MemoryTransport`）

### exe の隣の `scripts`

配布版の `Sashimono.exe` の隣の `scripts` は、**読む置き場として残す** 前の版の案内どおりそこへ
置いた人がいて、読むのをやめるとその人のスクリプトが更新の前から使えなくなる
ただし勧める置き場は `%APPDATA%\Sashimono\scripts`（〔互換〕→〔スクリプトフォルダを開く〕）

- 自動更新は入れ替える前に新しい版へ写す（`carry_user_files`） 前の版へ戻すときも戻る先へ写す
- zip を手で展開し直してフォルダごと入れ替えると消える（元のフォルダへ上書きで展開するだけなら残る）
- そこで、起動したときに `%APPDATA%\Sashimono\scripts` へ移す（`UpdateController.offer_script_move`
  起動の 3 秒後 `start_updates` の中） 好みは `Preferences.scripts_move`
  自動で移す（`auto` 既定 利用者の決定）・移すかを尋ねる（`ask` 同じ物は 1 度だけ）・何もしない（`off`）
  どれでも〔互換〕→〔exe の隣のスクリプトを移す…〕から移せる
- 移す決まり（`update/portable.py`）
  - 同梱の物（`BUNDLED_SCRIPT_FILES` 今は直下の `README.txt` だけ）は移さない 配る zip の `scripts` に
    物を足したら、ここにも足す（`tests/update/test_portable.py` が `build_package.assemble` と照らす）
  - 移し先に同じ名前があれば上書きせず、exe の隣に残して知らせる 別の名前で写すことはしない
    別の名前にするとスクリプトの名前（`aviutl:相対の場所:名前`）が変わり、同じ物が棚に 2 つ並ぶ
  - 作業用の名前（`<名前>.<プロセス番号>.moving`）へ写し、元と中身を照らしてから本来の名前を付け、
    それから元を消す 途中で失敗しても元は消さない 元を消せなかった物は数えて知らせる
  - 移して空になったフォルダは片付ける `scripts` そのものは残す
- **読む順は変わらない** 読む順は exe の隣 → `%APPDATA%` → AviUtl2 で、後に読んだ方が同じ名前で勝つ
  移すのはいちばん負ける exe の隣から次の `%APPDATA%` へだけで、`%APPDATA%` に同じ名前があれば
  移さない（前から `%APPDATA%` の方が勝っている） 名前は置き場からの相対なので、作品の中の名前も変わらない
- 知らせは 1 度だけ（`UpdateState.scripts_offered` に見た物を覚える） 自動で移した知らせは、窓を塞がない
  窓（modeless）で出す 塞ぐと、出ている間は編集画面を閉じられない（Windows の閉じる知らせも
  塞がれた窓には届かず、`check_clean_machine.ps1` の「閉じる知らせを送って待つ」が落ちる）
  ほかの窓（退避の復元など）を尋ねている最中なら、何もせずに次の起動へ回す
- まっさらな Windows の確かめ（`check_clean_machine.ps1`）は、exe の隣に見本を置いて起動し、閉じた後に
  `%APPDATA%` 側へ移ったことを見る

### リリースノート

下書きの本文は Release の workflow（`release.yml`）が雛形で作る 公開する前に「変わった所」を書く
雛形には「更新のしかた」（自動更新と手で入れ替えるときの違い、exe の隣の `scripts` が手で入れ替えると
消えること）が毎回同じ言い方で入る 消さない

#### Python が上がる版を出すとき

`python_abi`（配布版の Python の上 2 桁 `cp314` など）が前の正式版から変わる版は、字幕起こしと AI 連携を
入れた人が全員入れ直しになる（入れてある物は消さないが、入れ直すまで使えない 合わせて 2 GB を超える）

- **リリースノートの先頭に書く** 雛形は、前の正式版の目録（固定の URL）と zip の `build-info.json` を
  比べ、変わっていれば先頭に注意を入れる（初めての公開などで前の目録が読めなければ比べない）
  書くのは、入れ直しが要る機能・落とし直す大きさ（数百 MB から 2 GB 超）・時間（回線で数分から 20 分ほど）・
  締め切りの前は更新を後にすること
- `tools/release.py` は公開を尋ねる前の要約で、この版が置き換える目録（正式版は固定の URL、ベータは `beta`）
  と比べ、変わるなら目立つ注意を出す 読めなければ「確かめられない」と出す 先頭に書いたかを見てから y と答える
- アプリの側は、入れる前の確認に入れ直しの機能・大きさ・時間を出す（上の「自動更新の仕組み」）
- Python を上げる PR では、`build_package.py` の zip からの確かめ（後から入れる部品の読み込みまで）を
  通してから出す 後から入れる部品が新しい Python 向けの wheel を出していなければ、入れ直せない

### 自動更新の署名鍵

**Ed25519 の鍵を 2 本**（今使う鍵と予備の鍵）持つ 考え方は minisign と同じで、実装は cryptography
ソフトに埋め込むのは公開鍵だけ（`src/sashimono/update/signing.py` の `TRUSTED_PUBLIC_KEYS`）
どちらかで署名が通れば信じる 2026-10-03 に利用者が手元で作った 2 本を埋め込んである
（この版より前に配った版は鍵を持たないので、更新を確かめない 手で入れ直してもらう）

秘密鍵は**本人がパスワード管理アプリ（原本）とオフラインの控え（USB や紙）に置く** ビルド機・
リポジトリ・CI には置かない 署名はリリースのときだけ手元で行う
（前は Actions の Secrets に置くと決めていた（Issue #32）が、workflow を書き換えられる人なら誰でも
取り出せるので、2026-10 に利用者と決め直した）

鍵を作る（1 度だけ）

```
.venv\Scripts\python.exe tools\update_keys.py generate --out <鍵を書くフォルダ>
```

1. 今使う鍵と予備の鍵の合言葉を尋ねられる（12 文字以上 別々にしてよい）
2. `sashimono-update-current.key` と `sashimono-update-spare.key` ができる 中身は合言葉で包んである
   （scrypt と AES-256-GCM） 画面に出るのは公開鍵だけ
3. 出てきた 2 行を `src/sashimono/update/signing.py` の `TRUSTED_PUBLIC_KEYS` に貼り、PR で入れる
   **貼った版を配るまで、配った版は更新を確かめない**（鍵の無い版は黙って何もしない）
4. 鍵のファイルを、パスワード管理アプリの添付とオフラインの控えへ移し、書いたフォルダからは消す
   合言葉もパスワード管理アプリに置く 予備の鍵は普段使わないので、控えだけに置いてもよい

鍵を差し替える（今使う鍵を失くした・漏れたかもしれない）

1. 予備の鍵で署名して出せば、配った版はそのまま受け取る（両方を埋め込んであるため）
2. その版で `TRUSTED_PUBLIC_KEYS` を差し替える 漏れた鍵を外し、予備の鍵を 1 本目へ、
   新しく作った鍵（`update_keys.py generate` で作り直し、要る方だけ使う）を 2 本目へ
3. 差し替えた版を予備の鍵で署名して出す 配った版が受け取った後は、新しい組で回る
4. 2 本とも失くすと、配った版へ更新を届ける道は無い（手で入れ直してもらう） 控えを 2 か所に置く

公開鍵が手元の鍵と対になっているかは `tools\update_keys.py show <鍵のファイル>` で見る（合言葉は要らない）

### 自動更新のリリース

`__version__` を上げた PR を main へ入れ、CI と Package が通ったら、main の手元で 1 コマンド打つ

```
.venv\Scripts\python.exe tools\release.py <版> --key <鍵のファイル>
.venv\Scripts\python.exe tools\release.py <版> --key <鍵のファイル> --dry-run   （何も変えずに残りを見る）
```

`--key` に鍵を入れたフォルダを渡すと、中の `sashimono-update-current.key`（今使う鍵）を使う
予備の鍵で署名するとき（鍵の差し替え）は、そのファイルを直に渡す

道具（`tools/release.py`）は次の段を順に進める **どの段も済んでいれば飛ばす** 途中で落ちたら
公開せずに止まり、次に何をするかを出す 直してから同じコマンドを打てば、続きから進む

| 段 | すること | 済んでいれば |
|---|---|---|
| 1. 前提 | 引数の版と `__version__` が同じ 手元が main で汚れていない origin/main と同じ 出す commit の CI と Package が success（走っている途中なら待つ） gh が使える 鍵が `TRUSTED_PUBLIC_KEYS` にある | ─ |
| 2. タグ | `v<版>` を注釈付きで打って push する | push 済みのタグが main の歴史の中で同じ版の commit を指せば飛ばす それ以外なら止まる |
| 3. 組み立て | Actions の Release（`release.yml`）がそのタグで終わるのを待つ | success なら飛ばす 落ちていれば止まる |
| 4. 下書き | リリースが下書きか確かめ、zip を `dist\release` へ落として GitHub の digest と照らし、展開する | 落とした zip が同じなら落とし直さない 公開済みなら下の「公開済みに打ち直したとき」 |
| 5. ソース | 足りない物を `collect_sources.py` で集め、本体を上げ終えてから別の呼び出しで索引を上げる | 下書きの `sources-manifest.json` に載ったファイルが全部、同じ大きさと sha256 で下書きにあり、`sources-SHA256SUMS.txt` もあれば飛ばす 欠けていれば足りない分だけ上げ直す |
| 6. 自己診断 | 展開した zip を `build_package.py` と同じ確かめ（`--self-check` ほか）に掛け、アプリを起こして「GL で描けていたか y/N」と尋ねる（`--skip-launch` で起こさない） | 同じ zip で通した印（`dist\release\release-checked.json`）があれば飛ばす |
| 7. 目録と署名 | `update_sign.py` の manifest → sign（合言葉を尋ねる）→ verify → 下書きへ上げる | 下書きにあれば落として verify し、今の引数（`--minimum` など）と zip で作り直した目録と全部の項目が同じなら飛ばす 違えば止まり、消して打ち直すか前と同じ引数で打ち直すかを出す（道具は消さない） 手元に上げ損ねた署名済みの目録があれば同じく比べ、同じなら上げるだけ 違えば作り直して署名し直す |
| 8. 公開 | 版・zip の大きさと sha256・資産の数・署名した鍵を出し、**y と答えたときだけ**公開する 公開した後、固定の URL がこの版を指すかを見る | ─ |

- 公開は必ず人が y と答える 確かめを全部飛ばす旗は作らない 取り返しが付かないのは公開だけで、
  そこを機械に任せると、署名の通らない版や描けない版を配って全員の自動更新を止める
- 秘密鍵と合言葉は画面にもファイルにも出さない 合言葉は `update_sign.py sign` と同じく
  getpass で尋ねる 鍵を開くのは署名する一瞬だけ
- タグの後に main へ文書の直しなどが入っていてもよい 出すのはタグの commit で、CI と Package も
  その commit の物を見る（手元の HEAD は origin/main と同じであればよい）
- `--dry-run` は git と gh の読み取りだけをする（タグ・落とす・上げる・署名・公開をしない）
  zip が手元に無ければ、6 と 7 は「残り」として出る
- ベータ（`1.3.0b1` のような版）は、プレリリースとして公開し、目録を `beta` へ上げ直す
  正式版で `beta` のリリースがあれば、そちらにも正式版の目録を上げ直す
- 公開した後（beta へ上げる所・固定の URL の確かめ）で落ちたときは「公開は済んでいる」と出し、
  手で打つ残り（`gh release upload beta … --clobber` など）を並べる 公開の呼び出し自体が落ちた
  ときも、GitHub の側で公開まで済んでいれば同じに扱う（通信が切れただけのことがある）
- 公開済みに打ち直したとき zip や目録は差し替えない 公開されている目録と署名を落とし、下書きの
  ときに手元で確かめた写し（`dist\release\update.json` か `dist\release\remote\update.json`）と
  バイト列まで同じで、埋め込んだ鍵で通るときだけ、公開した後の残り（beta の目録・固定の URL の
  確かめ）を y で続ける 公開済みと分かった後はどこで止まっても「公開はしていない」とは出さない
  - 写しが無い・落とすのに失敗した：手で打つ残りを出す
  - 公開されている目録が写しと違う・公開に目録が無い：残りの手順は出さない（違う目録を beta へ
    広げない） 誰が差し替えたかを先に確かめる

中で何をしているか・道具が使えないときの手作業

```
1. __version__ を上げて main へ入れ、タグ v<版> を打って push する
2. Actions（.github/workflows/release.yml）がタグと版を照らし、zip を組み立て、リリースの下書きへ上げる
3. 下書きから zip を落とし、展開して Sashimono.exe --self-check | more で確かめ、起こして GL で描けるかを見る
4. 目録を作る    .venv\Scripts\python.exe tools\update_sign.py manifest <zip> [--minimum <版>]
5. 署名する      .venv\Scripts\python.exe tools\update_sign.py sign update.json --key <鍵のファイル>
6. 確かめる      .venv\Scripts\python.exe tools\update_sign.py verify update.json
7. 上げる        gh release upload v<版> update.json update.json.sig
                 （ソースの添付は上の「リリースにソースを添付する」）
8. 下書きを公開する（ここで初めて releases/latest/download/… が新しい版を指す）
                 gh release edit v<版> --draft=false --latest
```

- **公開した後・署名を上げた後に zip を差し替えない** 組み立て直した zip は SHA-256 が変わり、
  署名した `update.json` と食い違って、全員の自動更新が照合で止まる workflow は、同じタグを
  走らせ直したときに、公開済みのリリースか、`update.json` / `update.json.sig` を上げた下書きなら
  上げる前に止まる 組み立て直したいときは、下書きから目録と署名を消してから走らせ直し、
  4 からやり直す 公開した後に直すなら、版を上げて新しいタグで出す
- **6 が通るまで下書きのままにする** 公開した瞬間に固定の URL が切り替わるので、署名の無い
  目録を誰かに見せない（署名が無ければ配った版は黙って飛ばすが、その間は誰も受け取れない）
- workflow は秘密鍵を使わない（`contents: write` だけ） まっさらな Windows で zip から起動する
  確かめ（`package.yml` の clean-machine）が通らなければ下書きへ上げない GPU が無いので
  GL で描く確かめは 3 で手元で行う
- 目録は `update_sign.py manifest` が zip の中の `build-info.json` から版と Python を読んで作る
  手で書き直すと署名が通らなくなる（署名は目録のバイト列そのものに付く） 直すなら作り直す
- `minimum` は、この版へ自動では上げられない古い版の境 目録の形や入れ替えの手順を変えたときだけ上げる

ベータ

- ベータは `v1.3.0b1` のようなタグで出し、下書きをプレリリースとして公開する
  （`latest` はプレリリースを飛ばすので、正式版を受け取る人には届かない）
- ベータの目録は、動かすリリース `beta`（タグ `beta` プレリリース 1 つだけ作っておく）へ上げる

```
gh release upload beta update.json update.json.sig --clobber
```

- 正式版を出したら、`beta` にも正式版の目録を上げ直す（直し忘れても、ベータを受け取る人は
  正式版の目録も読むので、新しい方を受け取る）

## 8. README と Wiki の画面写真

**手で撮らない** 画面写真は `tools/shots.py` が撮る

```
.venv\Scripts\python.exe tools\shots.py
.venv\Scripts\python.exe tools\shots.py --list
.venv\Scripts\python.exe tools\shots.py --only screenshot subtitle
.venv\Scripts\python.exe tools\shots.py --wiki <Wiki の clone>
```

リポジトリの根から走らせる 撮れた物は `docs/` へ上書きされる
（`--output` で行き先を変えられる 先に別の場所へ出して見比べるとよい）
Wiki の手順書の写真は `--wiki` に Wiki の clone を渡したときだけ撮り、その `images/` へ書く
`--only` で手順書の写真を名指しするときも `--wiki` が要る

手で撮ると、撮った人の画面配置・重なった別の窓・本人のファイル名が写り込み、
画面が変わったときに同じ絵を作り直せない 道具は窓そのものを `QWidget.grab()` で
写すので、机の上に何が出ていても結果は変わらない 窓は机の上に出さずに描かせる
（`WA_DontShowOnScreen`） GL のプレビューもこのまま写る メニューは開くと別の窓に
なるので、机に出さずに開いて描かせ、メニューバーの下へ重ねる 手順書で押す所は
橙の枠で囲む

気を付けること

- **プレビューが真っ黒なら止まる** `QWidget.grab()` が GL の中身を拾うかは環境で
  変わるので、GL の面は `grabFramebuffer()` で取り直して重ね、明るさを見て確かめる
- 書き出しの窓の出力先は、ホーム（作業用のフォルダ）の部分を `%USERPROFILE%` と書き換えて撮る
- README の本文が名前を引き合いに出している見本（`見本の金文字` `回転しながら登場`）は
  `SAMPLE_ALIAS_NAME` `SAMPLE_YMM4_NAME` で名指ししてある 本文を変えたらここも変える
- 写真を撮り直したら、**README と Wiki の本文と食い違っていないか**を読み返す
  止めたフレーム・エフェクトの名前・写っている値は本文に書いてある Wiki の手順書の頭に
  撮った版を書いてあるので、版を上げて画面が変わったら撮り直して版も書き換える
- 撮った写真は 1 枚ずつ目で確かめる ユーザー名・フォルダの名前・配布物が写っていないか
